## P0：立即修复

### V1：注册端点加 H5 签名验证

**现状**
- [src/api/user/v1/open.js:32](../../src/api/user/v1/open.js#L32) 的 `/register` 路由未设 `requireSignature`
- 对比：登录接口 `/oauth21/v1/auth/login` 有 `requireSignature`（经 `verifySignature` 校验）
- 违反 CLAUDE.md「相同功能的不同入口路径必须具有相同级别的安全保护」

**风险**
- 攻击者绕过前端，直接高频调用 `/user/v1/register`
- 邮箱验证码 + 唯一约束兜底，但仍可被用于账号灌水、验证码耗尽攻击

**修复方案**
1. [open.js:32](../../src/api/user/v1/open.js#L32) `/register` 路由加 `requireSignature: true`
2. [src/api/verify/v1/verify.js:45](../../src/api/verify/v1/verify.js#L45) `/verify-captcha` 同步加 `requireSignature: true`（发码端点同属暴露面）
3. 前端注册页提交时补 H5 签名头（`oauth21/src/view/web/register/index.vue` + `app/register/index.vue`）
4. 确认 `registerSecureRoute` 的 `requireSignature` 透传到 `routeConfig.requireSignature`（[guard.js:407](../../src/api/guard.js#L407) 已有）

**验收**
- 不带签名头调 `/register` → 401 签名无效
- 带正确签名 → 正常注册
- 登录接口行为不变

### V2：check-email/username 枚举防护

**现状**
- [open.js:54-64](../../src/api/user/v1/open.js#L54) `/check-email`、`/check-username` 直接返回 `{isDuplicate: boolean}`
- 无频控、无签名，未登录可无限调用

**风险**
- 账号枚举：攻击者据此收集有效邮箱/用户名清单，用于撞库、钓鱼
- 注意：**不能删掉 isDuplicate**——用户填邮箱需即时提示"已注册去登录"，否则重复提交体验差。目标是防自动化枚举，不是隐藏存在性

**修复方案**
1. `/check-email`、`/check-username` 加 `requireSignature: true`（与 V1 同批，已做）
2. 加 IP 维度限频（复用 `@fastify/rateLimit`，已做：check 10次/分钟）
3. **保留 isDuplicate 响应**——正常用户体验需要"已注册"提示；限频 + 签名已足以抑制自动化枚举，无需改响应文案

**验收**
- 高频调用 `/check-email` → 429 限频（抑制脚本枚举）
- 无签名调用 → 401（必须先拿 _m_h5_tk cookie）
- 正常用户填邮箱 → 正常返回 isDuplicate 提示"已注册去登录"

## P1：本周修复

### V3：RSA 密钥轮换 + 日志脱敏

**现状**
- 密码 RSA 公钥加密传输、bcrypt 哈希存储（设计正确）
- 有 `kid` 多密钥机制（`getCachedKid`），支持轮换
- 风险点：RSA 私钥泄露后，传输中的密码（若请求日志记录 body）可被解密

**修复方案**
1. 确认 `src/app/oauth21/crypto/` 的旧 kid 私钥是否及时吊销（密钥轮换流程文档化）
2. 请求日志**禁止记录 body**（password/email/code 字段）——审计 `src/framework/log/` 的请求日志配置
3. 前端 `rsaEncrypt` 确认用最新 kid 公钥

**验收**
- 请求日志 grep 不到明文 password
- kid 轮换文档就绪

### V4：邮箱验证码绑定 session

**现状**
- [verify.js:53](../../src/api/verify/v1/verify.js#L53) `emailDao.sendCode(email, sessionId, store)` 以 email 为 key
- 待确认：`verifyCode` 是否校验"发码 sessionId == 用码 sessionId"

**修复方案**
1. 读 `src/framework/verify/email/index.js` 确认 sessionId 来源与校验逻辑
2. 若未绑定：验证码 key 改为 `email:sessionId`，`/register` 和 `/check-email-code` 用码时校验 sessionId 一致
3. sessionId 从客户端 cookie 或请求头获取（发码时下发，用码时回传）

**验收**
- A 浏览器发码，B 浏览器用码 → 失败
- 同浏览器发码用码 → 成功

### V8：注册审计日志

**现状**
- 登录有 `logLogin`（成功/失败），注册成功无审计记录
- 无法追溯"谁在何时注册了某账号"

**修复方案**
1. `src/framework/auth/audit-logger.js` 新增 `logRegister`（复用 logLogin 模式）
2. [user.dao.js](../../src/app/user/dao/user.js) `registerUser` 事务后调 `logRegister`，记录 ip/ua/email/time/role_ids
3. 注册失败（邮箱已存在/复杂度不足）也记录

**验收**
- 注册成功 → Redis/DB 有 audit 记录
- 注册失败 → 有失败 audit 记录

## P2：计划修复

### V5：consentKey 绑定客户端

**现状**
- [login.service.js:155](../../src/app/oauth21/services/login.service.js#L155) consentKey 存 Redis `consent_session`，TTL 300s
- `confirmDirectConsent` 持票即认，不校验客户端一致性

**修复方案**
1. `directLogin` 生成 consentKey 时，存入发起请求的 session 指纹（IP+UA hash 或 sid）
2. `confirmDirectConsent` 校验同一指纹，不一致则拒绝

**验收**
- A 客户端拿 consentKey，B 客户端调 confirm → 失败
- 同客户端 → 成功

### V9：默认 guest 角色失败明确报错

**现状**
- [user.dao.js:207](../../src/app/user/dao/user.js#L207) `Role.findOne({rank_level:1, app_id:'GLOBAL'})` 找不到则静默不绑角色
- 用户注册成功但无角色 → 权限为空

**修复方案**
1. guest 角色找不到时抛错（而非静默跳过），事务回滚
2. seed 数据保证 guest 存在（`09-pbac.js` 启动时同步）

**验收**
- guest 角色被删 → 注册失败明确报错（而非静默无角色）
- 正常情况 → 注册即有 guest 角色

### V10：directLogin 适用范围文档化

**现状**
- CLAUDE.md 的 OAuth 2.1 架构图描述授权码 + PKCE，但实际登录走 `directLogin`（直接换 token）
- 一方应用用 directLogin，三方走 consent + client_id 校验——混合模式未文档化

**修复方案**
1. `src/app/oauth21/CLAUDE.md` 明确：一方应用 = directLogin；三方应用 = 授权码 + PKCE + consent
2. directLogin 仅限 `FIRST_PARTY_APP`，三方 client 强制走标准流程

**验收**
- 文档明确两种模式适用范围
- 三方客户端无法走 directLogin（代码已有 `client.client_id !== FIRST_PARTY_APP` 分支）
