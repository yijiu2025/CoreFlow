01装配链路：注册顺序是功能性的

05-firewall.js 的三步编排顺序不可交换：第 ② 步注册的 @fastify/rate-limit v10 靠 onRoute 钩子给「此后注册的每条路由」挂限流配置 —— 一旦挪到 08-api 之后，插件装上了但 钩子一次都不会触发，全局限流静默失效。

启动
index.js → createApp() → runEngine() → registry 顺序执行
前序 loader：00-globals · 01-monitor · 02-redis(app.redis) · 03-db · 04-auth(Session + ALS)。防火墙必须在这之后、08-api 之前。
engine 装载 05
① app 侧前置（可选，存在才做）
prepareAppFirewall()  ·  app/firewall/index.js
调用 initDao() → registerSettingsReader() 注入磁盘配置读取器（interface/config-access.js 的 settingsReader 引用）； 再 registerEmailAlertSender() 注入「动态 import notice 邮件服务」的闭包。
为什么必须最先：registerRateLimit 在插件注册期就读 defense.enableRateLimit，晚读会拿默认值误判开关。
fs.existsSync 存在性守卫
② framework 防护核心（无条件启动）
firewallCorePlugin(app)  ·  framework/firewall/bootstrap.js
模块顶层的兜底：if (!hasSettingsReader()) registerSettingsReader(() => DEFAULT_SECURITY_SETTINGS) —— 保证 app 被卸载后仍能以 config/defaults.js 的默认策略矩阵独立运行。
内部依次：startCleanupTask(app) → registerRateLimit(app) → 注册 4 个钩子（见下节）。
③ app 侧收尾
收尾
firewallAppPlugin(app)  ·  fastify-plugin 封装
syncManualBlacklistToRedis() + syncManualWhitelistToRedis()：把配置里的手动名单灌进 Redis； app.addHook('onClose') → cleanupSaveTimer() + flushPersist()（遥测内存落盘）。
依赖倒置的三处「函数引用注入」（framework 不许 import app，全部靠注入）： interface/config-access.js（配置读取器）、telemetry-sink.js（遥测 sink，由 data/store.js 模块体里 registerRecordSink(pushRecord) 注册）、engine/auto-responder.js（邮件通道）。 三者未注册时都 fail-open 静默跳过，防护本身不受影响。

02请求主链路：onRequest 五阶段拦截管道

firewallCorePlugin 一共挂了 4 个钩子：两个 onRequest（主管道 + WebSocket 升级）、一个 onSend、一个 onResponse。 主管道在框架的 @fastify/cookie / auth / 全局 @fastify/rate-limit 之后执行。

框架前置（非防火墙代码，但决定防火墙能看到什么）
onRequest[0] @fastify/cookie → onRequest[1] auth → onRequest[2] @fastify/rate-limit（全局桶）
request.cookies 由 cookie 插件解析；request.state.user 由 auth 填充（sid → Redis session，过期用 sid_r 刷新）。 全局限流由 registerRateLimit 注册，keyGenerator 已登录用 rate:user:{id}、否则 rate:ip:{ip}。
进入防火墙 onRequest
阶段 0 · 上下文构建
buildRequestContext(request) → { ip, ua, fingerprint, deviceId, geoInfo }
写 request 三个隐藏字段：request._fingerprint、request._deviceId、request._firewallLog（一条含 time/ip/fingerprint/deviceId/method/url/userAgent/blocked + region,city 的日志草稿）。
调用：generateFingerprint(request)（sha256 前 16 位）· getClientDeviceId(request)（auth，只认客户端自报且校验通过，不补发）· resolveGeoInfo(ip)（geoip-lite）。

04存储层：Redis 优先，内存自动降级

访问层把「机制」收拢成语义操作，所有 key 都经 getStore('fw', {timeout:2000}) 自动加 fw: 前缀； redisAvailable() 为假或单次调用抛错时，同一套语义自动落到内存表 —— 调用方不需要写 if (!redis) 分支。

Redis 路径
store().call(client => client.eval(LUA_X, { keys, arguments }))
9 个 Lua 脚本承担全部原子性：读状态（1 次往返取 6 项）、写封禁（SET+HSET）、写白名单、DEL+HDEL、滑窗（4 命令合 1）、INCR+EXPIRE、签发令牌、校验令牌、GET+DEL。单次操作 OP_TIMEOUT_MS=2000，失败即降级。
Redis 不可用 / 调用抛错
内存降级路径
mem.blocks / blocksFp / blocksDev / whitelist×3 / counters / windows / passes / flags / challenges
11 张 Map，按 expiresAt 惰性过期，sweepMemory() 每 60s 清理一次。进程内状态：多实例各一份，Redis 恢复后不补写，重启即丢 —— 宁可弱化，不做假的强一致。
为什么两张「进程内表」坚持不走 getStore
activeConnections · ipRequestTimestamps
四条硬伤：① 无原子自增（读-改-写在并发下丢更新）；② 同步热路径→异步传染，+1/−1 各一次往返；③ 降级分叉（部分计数进 Redis、部分进内存，更难推理）； ④ 统计要全表（Redis 侧只能 SCAN）。MapStore 还有 maxSize 抛错风险 —— 洪水下新 IP 写不进，异常会被当成封禁错误回 429。
代价已知：放行上限 = maxConn × 实例数；Bot 频次按实例切分，多实例对低速爬虫会漏判。要跨实例精确限流，前移到边缘（Nginx limit_conn / ALB）。
