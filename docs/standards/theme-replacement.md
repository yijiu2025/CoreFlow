# 前端主题替换规范（主题包 × 设备 × 页面 × 配色）

> 适用项目：`oauth21`（登录 / SSO 中心）、`firewall`、`admin`、`posecraft` 及今后所有子前端。
> 本文是**可直接套用的规范**：定义目录契约、替换入口、优先级与红线，新项目照抄即可获得
> 「不改业务代码换 UI / 换配色 / 换明暗」的能力。
>
> 参考实现：`oauth21/src/theme/`（机制源码）、`oauth21/src/stores/theme.ts`（运行时状态）。
> 深度细节与演进记录见总文档 `oauth21/docs/multi-theme.md`；抽包设计见
> `docs/standards/theme-package-extraction.md`。

---

## 〇、一条原则

**换 UI 是配置，不是改代码。**

- 用户可见的三个维度彼此**正交**：配色（tokens 取值）、版式（DOM 结构）、明暗（mode）。
  换任何一个都不动另外两个。
- 每个概念只有**一个事实来源**：设备清单、默认值、id 白名单、优先级链，都只有一份实现，
  别的文件只转发不复制。抄第二份 = 制造漂移。
- 坏配置**静默跳过，不抛错**：一个写坏的目录不该让整个页面起不来（认证页起不来是事故）。

## 一、机制总览

```
                 ┌──────────── 四种替换入口（外部输入，全部过白名单）────────────┐
                 │ URL ?view=/?theme=/?skin=/?mode=（可带设备维度 .<设备> 后缀）  │
                 │ 主题包 / 配色记录里的 views 声明                              │
                 │ 部署级默认 VITE_<PAGE>_VIEW（.env，整站换 UI 不动代码）       │
                 │ 后端下发 GET {VITE_THEME_ENDPOINT}?client_id=（一构建产多品牌）│
                 └──────────────────────────┬───────────────────────────────────┘
                                            ▼
   版式（view）≡ 主题包（pkg） ─── 当前包 × 当前设备 ───> index.vue（长什么样）
                                            │
   配色（color）── 包/设备/页面/配色 四段键 ──> tokens + theme.scss（取什么值）
                                            │
   明暗（mode）── light/dark/system ────────> html.dark 基线 SCSS（与配色正交）
```

三个维度的落地形态：

| 维度 | 住在哪 | 换它等于 |
| --- | --- | --- |
| 版式 | `themes/<包>/<设备>/<页面>/index.vue` | 加一个主题包目录 |
| 配色 | `themes/<包>/<设备>/<页面>/colors/<配色>/` | 加一个配色目录 |
| 明暗 | 基线 SCSS 的 `:root` / `html.dark` + 每套配色自带的 `tone` | 切 mode / 选另一系别配色 |

## 二、目录约定（契约）

```
src/theme/                          # 架构层：机制，所有主题包共用一份
├── index.ts                        #   配色注册表构建 + 查询（findRecord/getThemeRecord/…）
├── registry.ts                     #   glob 扫描 → 注册表（构建层）
├── devices.ts                      #   设备清单：唯一声明处（id/label/路由/判定/容器）
├── runtime.ts                      #   token 注入 DOM（白名单校验后写根节点 inline style）
├── remote.ts                       #   后端下发的主题配置
├── mode.ts / tone.ts               #   明暗三态 / 配色系别
├── types.ts                        #   契约类型（MauthThemePackage/Color/Record）
├── views/                          #   版式机制（架构层，与主题包无关）
│   ├── page.ts                     #     页面工厂 defineThemePage：接入机制的唯一写法
│   ├── registry.ts                 #     版式注册表工厂（容器 + 可换 UI）
│   ├── picker.ts                   #     版式选择优先级：唯一实现
│   ├── params.ts                   #     设备维度 URL 参数 ?view.<设备> / ?theme.<设备>
│   └── <page>.ts                   #     每页一份：契约 + 注册表（login/register/…）
└── themes/                         # 主题包：一套完整设计
    ├── default/                    # 包定义 index.ts（只有 meta / 可选 views 声明）
    │   ├── mobile/                 # 该设计的手机端呈现
    │   │   └── login/
    │   │       ├── index.vue       #   ← 该包该设备该页的唯一版式
    │   │       └── colors/         #   ← 该页的配色（只换取值，不动 DOM）
    │   │           ├── white/index.ts        # 浅色底（tone: 'light'）
    │   │           ├── black/index.ts        # 深色底（tone: 'dark'）
    │   │           └── blue/{index.ts, theme.scss, assets/}
    │   ├── standard/               # 桌面主窗口呈现（结构同上）
    │   ├── mini/                   # iframe 紧凑版呈现（结构同上）
    │   └── tablet/                 # 平板呈现（结构同上；可只覆盖部分页面）
    └── compact/                    # 另一个主题包 = 另一种版式
```

**命名与合法性**

- **目录名即 id**：包名、设备名、页面名、配色 id 全部取自目录名，只允许 `[a-z0-9-]`。
  不合规的目录**静默跳过**（不抛错）—— 所以改错名字的症状是"什么都没发生"，
  排查时先核目录名。
- **页面名三处字面一致**：`themes/<包>/<设备>/<页面>/` 目录名 = `theme/views/<页面>.ts`
  文件名 = 路由 path 末段。
- 🔴 **一个主题包 = 一种版式**（`view ≡ pkg`）：`<页面>/` 下**只有** `index.vue` 与
  `colors/`，**没有**「版式」这一层目录。要另一种版式 → **新建主题包**
  （`themes/compact/<设备>/<页面>/`），不要建 `<页面>/<版式>/`。
  （早期支持过 6 段变体形态，已删除：它要求换版式时复制整套配色，两套必然漂移。）
- **设备是主题包内的一层**，不是顶层目录：一个包 = 一套设计语言，手机端与电脑端是它在
  两种设备上的呈现，住在同一个包里。「换一套设计」只需换一个包目录，不会出现版式换了
  配色没换、或两端各换一半。
- **配色在设备内独立配置**：`mobile/colors/` 与 `standard/colors/` 是两个互不影响的集合
  （目录名可以相同）—— 这正是「两端分别配置主题」的落点。

## 三、职责红线：业务容器 vs 版式

页面拆成两半，**边界就是这套机制的命根子**：

| | 业务容器 | 版式（UI） |
| --- | --- | --- |
| 住在哪 | `src/view/<设备>/<页面>/`（如 `view/app/login/index.vue`、`view/web/login/StandardLogin.vue`） | `src/theme/themes/<包>/<设备>/<页面>/index.vue` |
| 管什么 | 状态、校验、请求、路由跳转、所有「点了会发生什么」 | 只管「长什么样」 |
| 份数 | **每页每设备只此一份**，任何版式都不复制它 | 一个包一份，可有很多包 |
| 拿数据 | 自己持有 | 通过 props 拿容器给的 `ctx`（状态 + 操作函数）来渲染与回调 |

🔴 红线：

- **业务逻辑禁止进版式**：校验规则、请求调用只能住在容器里。版式里出现 `fetch` /
  校验函数 = 两份逻辑开始漂移。
- **版式只读 `ctx` / `ctx.actions`**：版式不直接 import store、不自己发请求。
- **容器静态引入自己设备的基础版式**：内置包（`default`）的版式是默认路径，
  由容器静态 import，零请求；非内置包才走惰性加载（见第八节）。

## 四、替换入口与优先级

### 4.1 版式（view）选择链（高 → 低，三页同形）

1. **URL `?view=<id>`** —— 本次访问的显式意图
2. **主题包 / 配色记录的声明** —— `views.<页面>`（包根 `index.ts` 写一次全包共用；
   写在某个 `colors/<配色>/index.ts` 里则只覆盖那一套）
3. **`VITE_<PAGE>_VIEW`** —— 部署级默认（`.env`，整站换 UI 不动代码）
4. **当前主题包名** —— 版式 id ≡ 包名，最差落"用当前包"

🔴 **第 1 档命中后不再回退**：`?view=typo` 落到**当前包**，而不是被声明或环境变量接管。
   显式参数写错时静默换用另一套 UI，比看到当前包的版式难排查得多。
🔴 **非法值一律落当前包名，绝不落 `'base'`**：`base` 只是「当前包的基础版式」的
   历史别名（会被归一到当前包名），不是合法包名。把 `'base'` 当包名传下去会让配色键
   全链落空 → **tokens 静默全丢、只剩余 SCSS 基线**（症状：页面配色无声变回基线，
   零报错）。
🔴 **`?view=<其它包名>` = 跨包切版式**：id 命中另一个包的登记即切到那个包
   （`?view=compact` 就是切到 compact 包）。

### 4.2 配色（theme）选择链（高 → 低，store 口径）

1. **用户显式操作**（点色卡 / 切明暗）—— 压过一切，且会清掉当前设备那条 URL 覆盖
2. **URL** `?theme.<设备>` / `?theme=` / `?skin=`（`skin` 是旧字段名，仍认）
3. **后端下发 / 父应用同步**（见第七节）
4. **localStorage**（用户上次选过的；URL 与后端都不落盘，只记录"这一侧的默认"）
5. 该范围默认色（先 `white`，没有则字母序第一套）

### 4.3 设备维度参数：同一链接，各端各配一套

`?view` / `?theme` / `?skin` 都支持 `.<设备>` 后缀，**取值链每台设备各一条**：

```
?theme.mobile=blue&theme.standard=black&view=compact
   手机端：theme.mobile → theme → 落盘 → 默认色   （拿到 blue）
   电脑端：theme.standard → theme → 落盘 → 默认色 （拿到 black）
   版式  ：view.standard → view → 包声明 → env → 当前包（三端都拿 compact）
```

- **设备专属优先，通用键兜底**：`?view.mobile=default&view=default` 前者赢。
- **空串 = 未指定**：`?view.standard=` 不会把 `?view=compact` 顶掉。
- **「锁」是逐设备的**：`?theme.standard=black` 只锁电脑端，手机端仍照常接收后端下发。
- 设备专属参数**不落盘**（与"URL 不落盘"同一纪律）。

### 4.4 设备判定（有哪些设备、这次访问算哪台）

设备清单是**唯一声明处**（`src/theme/devices.ts` 一条 `ThemeDeviceDef` = 一种设备），
清单顺序即判定优先级：

| 顺序 | 设备 | 命中条件 | 路由 path |
| --- | --- | --- | --- |
| 1 | `mini` | `?from=mini` / `?fromLogin=mini` / 路径段 `mini-`（排除 `?isMobile=true`） | `mini-<page>` |
| 2 | `tablet` | `?from=tablet`（排除 `?isMobile=true`） | `tablet/<page>` |
| 3 | `mobile` | `?isMobile=true` 或视口 / UA 判定为移动端 | `m/<page>` |
| 4 | `standard` | **兜底：无条件命中，必须是最后一条** | `<page>` |

- 🔴 **显式意图 > 来源标记 > 视口**：`?isMobile=true&from=mini` 按手机端走。
- 视口判定必须**响应式**（拉宽窗口要能自动切回桌面），不能是一次性快照。
- 该设备没写某一页的容器时，**退到 standard 的容器**，不是起不来。

## 五、token 分层与注入（换配色的落地）

三层，优先级低 → 高：

1. **SCSS 基线** —— `:root` / `html.dark` / 断点块（没有主题机制时的渲染路径）
2. **主题包 tokens** —— `getThemeRecord(...).tokens`（每个 `colors/<配色>/index.ts` 自带）
3. **外部覆写 tokens** —— 后端下发 / 父应用同步

第 2、3 层都写在 `documentElement` 的 inline style 上（优先级高于任何选择器），
层间顺序靠**写入顺序**保证：先写主题包、再写外部覆写，同名后者胜。每次注入做
**差集清理**：换配色后上一轮的变量会被 `removeProperty`，不残留旧值。

🔴 安全边界：

- 外部 token **必须过白名单校验**（名字 `--mauth-` 前缀 + 取值限颜色 / 长度 / 关键字 /
  var 引用），逐条过滤、丢弃并告警。CSS 自定义属性是能直接改变渲染的输入，未校验就
  `setProperty` 等于把样式注入的口子交给后端或父页面。**走白名单，不走黑名单。**
- 主题包自己的 `theme.scss` 不走这条通道 —— 那是构建期就在仓库里的受信代码。

🔴 tokens 是**一组扁平值，不分明暗档**：每套配色**自带完整底色**，选谁就是谁
（不会出现「选了黑再选蓝，底色还是黑」）。需要深色版品牌色 → **另加一个配色目录**
（如 `navy`），而不是做"某配色的深色档"。

## 六、明暗（mode）与配色系别（tone）

- **mode 三态**：`light` / `dark` / `system`（`system` 是显式跟随系统，随时可回）。
- **系别（tone）跟着每套配色走**：`white.tone='light'`、`black.tone='dark'`，
  与 blue/cyan/rainbow **平级**，可以显式选中、出现在列表里。
- **明暗与配色永远一致**：`isDark = 当前配色的系别`。点黑卡即暗、点白卡即明；
  切「暗」落到黑系、切「明」落到白系（两侧各自记住上次选的配色）。
- **跨作用域回落保持系别一致**：请求的 id 没登记在当前作用域时（如 `blue` 只在手机端
  有），取它的系别在本作用域的首套（浅底选浅底、深底选深底）—— 否则"把窗口拉宽"
  就会让页面在黑白之间翻转。
- ⚠️ 某作用域**没有**目标系别的配色时，**什么都不做**，不跨系别硬凑
  （否则"开夜间"会拿到一套浅底，看起来像没生效）。
- **版式 / 设备不匹配时不跨包借配色**：拿紧凑包的 token 渲染基础版式会得到一套尺寸 /
  圆角都对不上的东西，不如老实用基线。

## 七、后端下发（远程主题：同一份构建产物服务多个品牌）

**接口契约**：`GET {VITE_THEME_ENDPOINT}?client_id=<clientId>`

```jsonc
// 200 OK
{
  "theme": "blue",          // 可选。已登记的配色 id
  "skin": "blue",           // 可选。theme 的旧字段名，二选一即可
  "mode": "dark",           // 可选。'light' | 'dark' | 'system'
  "tokens": {               // 可选。一组扁平的 CSS 变量覆写（白名单校验）
    "--mauth-primary": "#0e7490",
    "--mauth-radius": "16px"
  }
}
```

- **默认关闭**：未配置 `VITE_THEME_ENDPOINT` 时整个机制不生效（不发任何请求、
  零副作用）—— 后端还没做这个接口时前端完全无感。
- **失败策略**：超时（3s）/ 非 200 / 结构不符，一律**静默返回 null**（用内置配色继续）。
  主题是"锦上添花"，绝不能因为拉不到配色挡住登录 —— 不抛错、不重试。
- **免鉴权公开端点**：请求不带 cookie（`credentials: 'omit'`），避免把登录态发到第三方域名。
- **只挑认识的字段**：响应结构由后端决定，多一个字段少一个类型都可能让后续代码出错，
  所以显式挑选，不透传。
- 🔴 `theme` 只能指定**已登记**的配色 id，后端不能下发 CSS 正文；需要更高自由度
  （背景图、字体）走 tokens + 前端主题包。
- 🔴 后端下发的 mode/theme **不写入 localStorage**：它们是「本次访问的部署方默认」，
  用户手动切过的偏好优先级更高。URL 命中的设备被「锁定」，后端下发不覆盖它。

## 八、加载与性能（按需是硬要求）

| 资产 | 策略 | 理由 |
| --- | --- | --- |
| `colors/<配色>/index.ts`（meta + tokens） | **同步预载**（glob eager） | 体积几百字节；URL 合法性校验、`data-mauth-theme` 属性写入都发生在首帧前，必须同步拿到 id → tokens 映射，否则先渲染默认色再跳变 |
| `colors/<配色>/theme.scss`（背景图 / 字体） | **惰性动态加载**（`?inline` 拿编译后 CSS 字符串，运行时插 `<style>`，切换时整体替换） | 真正有体积的部分；Vite 给每套配色单独切 chunk，切到才请求 |
| 内置包（`default`）的版式 | 容器**静态 import** | 默认路径多等一个网络往返不划算；注册表对内置包直接返回 null = "用你静态引入的那份" |
| 非内置包的版式 | **惰性 + 路由守卫预热**（`preload` 不 await） | 包是运行时才定的，静态 import 钉不住；容器首帧先渲染静态兜底、chunk 到了再接管 |

⚠️ 惰性加载会被 PWA 预缓存破坏（"惰性"全部被拉回来）—— 需要 PWA 的项目要么把主题
   资产排出预缓存，要么整体移除 PWA（`oauth21` 已整体移除，原因见 multi-theme.md 第五节）。

## 九、加东西的清单

### 9.1 加一套配色（在已有主题包的某个页面下）

1. 建目录 `themes/<包>/<设备>/<页面>/colors/<新色>/`
2. 写 `index.ts`：`export default { meta: { id, name }, tone: 'light' | 'dark', tokens: {...} }`
   （`tone` 类型上必填；漏写运行时按 `light` 兜底并告警）
3. 需要背景图 / 自定义字体 → 同目录加 `theme.scss`（自动被惰性加载）
4. 完成：出现在调试面板、可被 `?theme=<新色>` 选中、参与明暗联动

### 9.2 加一种版式 ＝ 加一个主题包

1. 建 `themes/<新包>/index.ts`（包定义：`meta` + 可选 `views` 声明）
2. 建 `themes/<新包>/<设备>/<页面>/index.vue`（该设备该页的唯一版式；读 `ctx` 渲染）
3. 配色：包内没有 `colors/` 也能跑（走 SCSS 基线）；要随包带色就按 9.1 加
4. `?view=<新包>` 即刻可切；也可在包定义里写 `views.<页面>` 让某套配色默认用它

### 9.3 加一种设备（如未来的 `tablet`）

1. `src/theme/devices.ts` 加一条 `ThemeDeviceDef`（id / label / routePath / match / containers）
2. 写它的容器：`view/<设备 id>/<页面>/index.vue`（或像 mini 那样指定自己的 glob 与文件名规则）
3. 在主题包里加该设备的目录：`themes/<包>/<设备>/<页面>/{index.vue, colors/}`
   （只覆盖部分设备 / 页面是允许的）
4. 🔴 清单**最后一条必须无条件成立**（兜底设备）；判定顺序就是清单顺序，先命中先用

### 9.4 接入一个新页面

1. `theme/views/<页面>.ts`：一次 `defineThemePage({ page, title, titles, envView, loaders })`
   声明（`page` = 目录名 = 文件名 = 路由末段；glob 模式必须是字符串字面量，所以写在页面文件里）
2. 各设备的业务容器：`view/<设备>/<页面>/index.vue`（静态引入内置包版式做首帧兜底）
3. 主题包内建该页目录（至少内置包要有，否则落到标准容器 + 基线样式）
4. 路由由页面注册表生成，不用手写

## 十、安全边界（外部输入全部过白名单）

| 入口 | 规则 |
| --- | --- |
| 配色 id | `resolveThemeId`：trim + lowercase，字符白名单，**必须已登记**；未登记返回 null 由调用方回退。**不做模糊匹配**（防 `../` 路径拼装绕过） |
| 版式 id | 同规则：当前包 × 当前设备内已登记才认；`base` 别名归一到当前包名，绝不当合法 id 返回 |
| 设备名 | 只认设备清单里的值；不认识的落默认设备 |
| 外部 token | `--mauth-` 前缀 + 取值白名单，逐条过滤并告警（见第五节） |
| 注册表容错 | 目录名不合规 / 缺 `export default` / 设备名不认识 → **跳过不抛错**；同范围重名 → 先到先得 + `console.warn`，不静默覆盖 |
| iframe 父应用 | postMessage 只发 / 只收命中 `VITE_ALLOWED_PARENT_ORIGINS` 的父 origin（防窃登录态、防伪造主题消息） |

## 十一、验收清单（新项目接入后逐条核）

- [ ] 目录口径：不存在 `<页面>/<版式>/` 变体层；glob 只有 `themes/<包>/<设备>/<页面>/colors/<配色>/` 一种形态
- [ ] 页面名三处一致（目录 / `views/<page>.ts` 文件名 / 路由末段）
- [ ] 设备清单末条无条件成立；三个分发器对 mini 来源口径一致（同一份 `devices.ts`）
- [ ] `?view=不存在的值` 落到当前包（不是 base、不是另一套 UI）；页面配色无声变回基线 = 有地方把 `'base'` 当包名用了
- [ ] `?theme.mobile=blue&theme.standard=black` 两端各生效；空串 `?view.standard=` 不顶掉通用键
- [ ] 换配色后上一轮 token 无残留（差集清理生效）
- [ ] 外部 token 白名单：下发 `--evil` / `url(...)` 被拒并告警
- [ ] 后端接口不通时页面照常渲染、无报错、无失败请求（未配置端点时零请求）
- [ ] 关卡自己"会红"：故意建一个坏目录 / 删一条设备声明，验证守卫真的报错（毒丸验证）
