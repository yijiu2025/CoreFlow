# 测试合理性审查提示词集（CI / e2e / 单测）

> 用途：把下面任意一条提示词**原样粘贴**给 AI（本对话或其他会话），即可对指定范围的测试代码
> 做一次「只读审查」。提示词是自包含的 —— 不需要额外解释背景，AI 按词执行即可。
>
> 适用本项目三类测试资产：
>
> | 资产 | 位置 | 运行方式 |
> | --- | --- | --- |
> | CI 门禁 | 根仓 `.github/workflows/ci.yml` | push/PR 自动 |
> | 后端单测 | 根仓 `src/__tests__/`（82 个 `.test.js`，Jest ESM） | `npm test` / CI `test` job |
> | 前端单测 | `oauth21/__tests__/` + `oauth21/src/**/__tests__/`（5 文件 47 例，vitest） | `npm run test --prefix oauth21` |
> | 前端验收关卡 | `oauth21/e2e/verify-*.mjs`（22 活跃 + 2 测量 + 2 毒丸） | `node oauth21/e2e/verify-all.mjs` |
> | 跨进程关卡 | 根仓 `scripts/verify/*.mjs` | CI `verify` job（带 Redis） |

## 提示词 A：CI 测试配置合理性审查

```text
你是 CI 工程审查专家。对【仓库根目录的 .github/workflows/ci.yml】做一次只读审查，
判断"CI 跑的测试是否合理"。不要修改任何文件，只输出审查报告。

背景事实（已核实，作为判断基线，不要重新质疑）：
- 本仓是 Node ESM 后端（Fastify + Jest）+ 三个独立前端工程（oauth21 / posecraft / firewall）。
- oauth21 是独立 git 工程（有自己的 package.json/lock/node_modules），不是 workspace 成员。
- 根 package-lock.json 把 wb-logkit 记为 link:packages/log，而该目录被 gitignore 排除。
- packages/theme-core 是 git submodule；packages/shared-device 是 workspace 成员。

审查步骤与判据（逐条给出结论 + 证据文件:行号）：
1. 覆盖面：每个"本可以拦住回归"的风险，是否都有对应 job 或步骤？
   对照四类：lint / 单元测试 / 前端（类型+规范+单测+构建）/ 需要真实环境的跨进程关卡。
   列出"CI 没跑但本地规范要求跑"的缺口。
2. 安装口径：每个 job 的 npm 安装命令是否与其依赖图匹配？
   - 走 npm ci 的：lock 必须入库、缓存才可开；
   - 走 npm install 的：是否有无法用 ci 的实证理由（如悬空软链）并在注释中记录；
   - submodule / workspace 依赖是否在 checkout/install 步骤中被满足。
3. 门禁顺序与失败语义：步骤顺序是否"便宜的在前"（类型→lint→单测→构建→重环境）？
   退出码是否区分"断言失败(1)"与"环境不可用(3)"？环境未就绪被误判成失败或放过，都是缺陷。
4. 缓存与并发：cache 是否只在 npm ci 路径上开？concurrency 是否取消了同分支旧流水线？
5. 假绿风险：有没有"命令永远 exit 0"的步骤（如未接断言的文件存在性检查、
   被 `|| true` 吞掉的命令、从不失败的 smoke test）？逐一列出。
6. 噪音风险：有没有"长期红/被 skip"的步骤会掩护真红？

输出格式：
- 总评：合理 / 基本合理（列出必须修的问题）/ 不合理
- 问题表：编号 | 位置(file:line) | 问题 | 严重度(高/中/低) | 建议修法
- 做得好的部分（≤3 条，避免审查报告变成全否定）
```

## 提示词 B：e2e / 验收关卡代码审查

```text
你是前端验收关卡（e2e verify scripts）审查专家。对【指定目录下的 verify-*.mjs】
做只读审查，判断每个关卡"是否合理、是否还有效"。不要修改任何文件。

判据（逐关卡核对，给出结论 + 证据 file:line）：
1. 测的是真东西：断言必须读取真实产物（落盘文件 / 真实构建输出 / 真实模块加载），
   禁止用手写常量当期望值自说自话。发现"期望值是硬编码、与被测物无推导关系"的判为假绿。
2. 反面对照：断言"某事物为 0/不存在"的关卡，必须同时证明"待测事物确实存在过"
   （否则 0 是假绿）。例如"产物无 console"必须对照"源码里确有 console"。
3. 毒丸自证：关卡是否有对应毒丸脚本（故意改坏必须变红）？没有的列为"未自证"。
   注意：不是每个关卡都需要毒丸，但"宣称守核心不变量"的必须有。
4. 退出码语义：0 通过 / 1 断言失败 / 3 环境不可用（或缺产物）是否区分？
   把"没起服务"报成"失败"或偷偷放过的，都是缺陷。
5. 恒绿/长红风险：
   - 断言条件永远成立（如断言一个常量等于它自己）；
   - 期望值写死且已与被测物漂移（应红却绿）；
   - 关卡是否已实际接入统一入口（verify-all 类编排器）？散落未接入=没人跑。
6. 过期关卡：被测特性已删/已改的关卡必须显式退役并记录原因，
   不许留在活跃列表里当噪声。发现"引用已删除文件/特性"的关卡，判退役。
7. 可读性：文件头是否写清"为什么有关卡、守什么、退出码"？无理由的关卡不可维护。

输出格式：
- 关卡清单表：关卡名 | 测什么 | 真东西✓/✗ | 反面对照✓/✗/不适用 | 毒丸✓/✗/不适用 | 退出码✓/✗ | 结论(健康/需修/应退役)
- 问题表：编号 | 关卡 | 问题 | 严重度 | 建议
- 明确回答：哪些关卡现在就能发现真实回归，哪些不能（以及为什么）
```

## 提示词 C：单元测试代码审查（`__tests__/`）

```text
你是单元测试审查专家。对【指定测试目录】做只读审查。不要修改任何文件。

先运行测试套件记录基线（多少个文件/用例通过），再逐文件审查：
1. 测的是被测代码：测试必须真实 import/mount 被测模块。禁止把实现逻辑复制进
   测试文件自测（那是测副本，被测物改了测试照样绿）。
2. 断言锁行为不锁实现：断言对外可观察结果（状态/输出/DOM），不断言"某私有函数
   被调用"。重构会改函数名/位置，那不叫回归。
3. mock 边界：只 mock 边界依赖（网络/时间/存储）；mock 掉被测模块的内部协作者 =
   测试手写常量。检查每个 vi.mock/vi.fn 是否落在边界上。
4. 脆弱选择器：优先用角色/文本/语义定位；class 名（如 .bg-slate-50）和
   位置选择器（button:first-child）随样式重构即失效，列为脆弱点。
5. 状态污染：store/单例/全局（localStorage、window.location、pinia 实例）是否
   在每个用例间重置？跨用例共享可变状态的测试会随机红。
6. 数据构造：fixture 是贴近真实数据（含边界：空/缺字段/超长/非法值），
   还是只有一条 happy path？列出缺失的边界场景。
7. 假绿风险：有没有 catch 后不断言的用例、expect 写在 if 里的用例、
   被 it.skip 跳过的用例？逐一列出并说明影响。

输出格式：
- 基线：X 文件 / Y 用例，通过/失败数
- 逐文件表：文件 | 测什么 | 真加载✓/✗ | 锁行为✓/✗ | 污染✓/✗ | 边界覆盖(全/中/无) | 结论
- 脆弱选择器清单（file:line + 建议替换成什么）
- 优先级排序的修复建议（≤5 条，按"能防住的回归价值"排序，不追求 100% 覆盖率）
```

## 提示词 D：测试有效性元审查（专找"测了等于没测"）

```text
你是测试有效性审计专家。任务：在【指定测试范围】里找出"存在但抓不住回归"的测试。
只读审查，不修改文件。按以下 hunt list 逐类排查，每类给出实例或明确写"未发现"：

H1 恒绿断言：条件永远为真（断言常量、断言 mock 自身返回值、空数组 forEach 里 expect）。
H2 复制式自测：测试文件里重新实现了被测逻辑，测的是副本不是真身。
H3 过期期望：期望值写死，被测物已变更（应红却绿）。找"最近改过源码但测试没动"的点。
H4 被吞的失败：try/catch 不断言、expect 在条件分支里、it.skip/xit、describe.skip。
H5 无入口：测试文件/关卡没被任何 CI job 或编排器引用（git grep 它的文件名）。
H6 伪覆盖：覆盖率数字高但断言浅（只调用了函数、没验证返回值/副作用）。
H7 毒丸缺失：宣称守"静默失效类"风险（配置写错无声、构建产物漂移、别名漂移）的
   关卡，却没有毒丸脚本证明它会红。

对每个发现输出：编号 | 类型 | 位置(file:line) | 为什么抓不住回归 | 最小修法。
最后给总结论：当前测试体系能防住哪几类回归，防不住哪几类（按风险排序）。
```

## 附：本项目现状基准（2026-10-15 实测，供审查时对照）

| 项 | 实测值 | 说明 |

| 后端单测 | `src/__tests__/` 82 个 `.test.js`，Jest ESM，`--experimental-vm-modules` | jest.config.js 有 coverageThreshold（branches 30 / functions 40 / lines 40 / statements 40）与 `.tmp-probe` 排除注释 |
| 前端单测 | 5 文件 47 例全绿（vitest + happy-dom） | theme store 27 例（resetModules 快照重置）/ ConsentPanel 6 例（真挂载）/ readDeviceParam 7 / parent-origins 4 / SCSS baseline 守卫 3 |
| 前端验收关卡 | 22 活跃（8 静态 + 9 dev + 3 特殊端口 + 2 生产构建）+ 2 毒丸 + 2 测量 | 权威索引 = `oauth21/e2e/VERIFY.md`，19 个已退役关卡有原因记录 |
| 关卡质量基线 | 真实产物断言、反面对照、毒丸自证、退出码 0/1/3 | 例：verify-console-strip 自建构建扫产物 + 源码对照；verify-kernel-zero-coupling 判据由 package.json 清单派生 |

| 已知薄弱点 | ① ConsentPanel.test.js 用 class 选择器与位置选择器（脆弱）；② 其 i18n 为手写 fixture，不断言真实语言包 key 存在；③ 根仓 `tests/` 目录是 10-08 调试截图残留（45 文件，未入库） | 审查时优先核对这三点是否已被修复 |

> 提示词使用注意：审查范围大时先把"指定目录"换成真实路径（如
> `oauth21/e2e/`、`oauth21/__tests__/`、`.github/workflows/`），并要求 AI
> **只输出报告不改代码** —— 修复决策人审查报告后再单独发起。
