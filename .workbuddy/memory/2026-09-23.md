## 一、排查「手机端 register 顶部有一条背景色」（小米浏览器可见、电脑 Chrome 不可见）

### 结论 1：「电脑看不到」的直接原因是**根本不是同一个页面**（已实测）

`oauth21` 有「宽视口 ≥1024 → 电脑版」的分发逻辑。实测（1440×900，无 UA 伪装）：

| 打开 | 最终 URL | 移动端 DOM | 进度条 |
| --- | --- | --- | --- |
| 宽视口 `/m/register` | **`/register`（被跳转）** | ❌ | ❌ |
| 宽视口 `/register` | `/register` | ❌ | ❌ |
| 窄视口(390) `/register` | `/register` | ✅ | ✅ |
| 窄视口(390) `/m/register` | `/m/register` | ✅ | ✅ |
| 安卓 UA + 宽视口(1440) `/m/register` | **`/register`（被跳转）** | ❌ | ❌ |

→ 在电脑上调试移动端页面，**必须在 DevTools 里模拟窄视口，且模拟后要刷新**
（分发在导航时执行，只拖窗口不刷新不生效）。
UA 伪装**不能**压过宽视口判定 —— 判定顺序是「宽视口 > 窄视口 > UA」。

### 结论 2：页面可见表面**全是 #fff**，露底暴露的是 body 底色

实测各层 `backgroundColor`：

```
html          rgba(0,0,0,0)     ← 透明
body          rgb(255,255,255)  ← Tailwind bg-background（浅色档 #fff）
#app          rgba(0,0,0,0)     ← 透明
div.min-h-screen  rgba(0,0,0,0) ← 透明（Tailwind min-height:100vh）
.mauth-page   rgb(248,250,252)  ← --mauth-bg，被下两层完全盖住
.mauth-header rgb(255,255,255)  ← var(--mauth-surface)
.mauth-body   rgb(255,255,255)  ← var(--mauth-surface)
.mauth-progress rgb(241,245,249) ← 进度条轨道，register 独有
```

- `.mauth-page` 的 `#f8fafc` 被 header + body（各 #fff）**完全覆盖** → 页面上不存在可见的浅灰条。
- header 白 vs page 灰的色差只有 **ΔRGB(7,5,3)** —— 正常显示下肉眼不可辨。
- 人为制造空隙（`.mauth-page` 下移 40px / 高度减 60px）后，`elementFromPoint(4,1)` 命中的是
  **`div.min-h-screen`（透明）** → 即**露出来的是 body 的 `#fff`**，与页面上其他白**同色**。
- ⚠️ 由此得出一条结构性隐患：**三处表面（header/body/page）不统一 + 外层全是透明容器**，
  一旦有"没铺到"的区域（安全区 / 视口高度差 / 回弹），露出的是**不可控的 body 底色**。
  正常路径下同色所以看不出，异常路径下就会变成"一条"。

### 结论 3：`env(safe-area-inset-top)` 可在桌面 Chrome 精确模拟（本轮最有价值的调试手段）

CDP **`Emulation.setSafeAreaInsetsOverride` 可用**（Chrome 153 实测）：

```
不改动        : safeTop=0px   .mauth-header paddingTop=24px  headerH=191
注 insets top=47: safeTop=47px  .mauth-header paddingTop=71px  headerH=238
```

→ 刘海屏安全区会**只加高 header**（顶部多出一条**纯白**），不会产生"另一种颜色"的带子。
所以「顶部一条背景色」若颜色是白，安全区是候选；若是别的颜色，**不是**安全区。

### 无效实验记录（避免下次误判）

- CDP `Emulation.setAutoDarkModeOverride({enabled:true})` → 各层背景色**零变化**。
  它只是让 UA 样式/媒体查询走上深色分支，**不等价于 MIUI 浏览器的"智能反色"**。
  ⚠️ **不能据此排除"浏览器强制深色"这个候选**（机制不同，属静默失效的归因实验）。

## 二、小白条根因定案 + 修复（用户反馈「没有从根本解决问题」）

### 结论 A：「是不是不同内核初始值不同」——**是**，而且规范是主动留白的

1. `color-scheme` 初始值 `normal`（不承诺配色）→ **画布（canvas）底色、表单控件、滚动条、系统色关键字**
   全由 UA 决定；叠加 CSS 2.2 §14.2「根背景向上传播成画布背景；若最终仍是 `transparent`，
   **渲染是未定义的**」。本仓此前**从未声明过 `color-scheme`**（grep 全仓命中 0）。
2. `vh ≡ lvh`（大视口）而 `dvh` 是动态视口 → 真机地址栏出现时 `100vh > 100dvh`（典型 56~80px）；
   **桌面 DevTools 不模拟动态浏览器 UI**，`vh === dvh` ⇒ 缝恒为 0 ⇒ **"电脑 Google Chrome 看不到"**。
3. 国产魔改内核还有第三层：合成器层 `filter: invert()`（夸克/QQ/UC/小米）——`color-scheme` 拦不住。

### 结论 B：白条是**我们自己上一版改动造出来的**，机制已实测复现

`App.vue` 与 `BlankLayout` 都是 `min-h-screen flex items-center justify-center`，`.mauth-page` 是 `100dvh`
→ 真机上容器比页面高 → **页面被垂直居中**，上下各留 `(100vh−100dvh)/2`；缝里露出的是**祖先底色**。
上一版把祖先链染成 `--mauth-header-bg`(#fff) → 缝从"与页面同色(#f8fafc)"变成**纯白**。

实测（390×844 DPR2，容器加高 120px 等价模拟 `vh−dvh=120`）：

| | 改前 | 改后 |
| --- | --- | --- |
| `.mauth-page`.top | **60** | **0** |
| 顶部像素 | 0..119 纯白 `(255,255,255)` → 120 起 `(248,250,252)` | 0..299 全部 `(248,250,252)` |

用户真机截图 y≈330 纯白、y≥360 `(249,250,252)` —— 同一条带子，只是 `vh−dvh` 更大。

### 修复（3 处代码）

1. `mobile-auth.scss`：`.mauth-page { align-self: flex-start; }`（**不依赖 `:has()`**，真正的兜底）
2. `mobile-auth.scss`：新增唯一兜底色 `--mauth-canvas` = "页面最上沿的颜色"
   （有 header 跟 header / 占位态跟页面底色），`html`+`body`+`.min-h-screen` 三处统一
3. `main.scss`：新增「跨内核初始值同步」段 —— `color-scheme: light / only light`（+ `html.dark` 深色档）、
   `-webkit-text-size-adjust:100%`、`html` 显式背景 `var(--mauth-canvas, hsl(var(--background)))`
   附加：`sky/theme.scss` 声明 `--mauth-canvas: var(--mauth-sky-top)`；契约写进 `themes/README.md` + `types.ts`

## 二、夸克浏览器"比例不对"（20:40 起）：内核丢掉 viewport meta

用户报"小米头部的条修好了，夸克还是这样"，随后更正："夸克没条，是比例不对"。

### 诊断：真机截图反解 → 布局视口 980 + 整页缩放 1.2245

量测用户截图（1200×2670）六项几何，再在 Chromium 里跑候选视口、把 DOM 几何换算成同物理尺度比对：

| 量测项 | 真机 | 980 视口 ×1.2245 | 400 视口 |
| --- | --- | --- | --- |
| 进度条宽 1142 / 按钮宽 1152 / 按钮高 59 | — | **1141.2 / 1151 / 58.8** | 1056 / 1080 / 144 |
| 字段高 57-58 / pitch 105 / 末字段→按钮 115 | — | **58.8 / 105.3 / 115.1** | 144 / 258 / 282 |

六项全落 1px 内 → 机制锁死：**980 布局视口 + 整页等比缩放 1.2245**（= 1200/980）。

### 关键排除实验（三个候选判据，只有第三个成立）

| 候选 | 实测 | 结论 |
| --- | --- | --- |
| `clientWidth` | `<head>` 解析期**恒为 980**，正常页也是（meta 要到首次布局才生效） | ❌ 会在正常手机误触发 |
| `screen.width` | 有的内核报物理像素（1200）；除 dpr 又会把 iPad(1024/2) 误判成手机 | ❌ |
| `visualViewport.scale` | 正常页 `1`、异常页 `0.4082`（与真机缩放比吻合），与 screen/dpr/UA 无关 | ✅ |

也实测确认：**加载后插入 meta 无效**（head 内插入才生效）→ 不能靠"运行时补 meta"兜底。

2. `oauth21/src/utils/viewport-fix.ts`（新）：按 `visualViewport.scale` 判定，`zoom = 1/scale`

3. `oauth21/src/assets/styles/mobile-auth.scss` §13：`html[data-mauth-vpfix] .mauth-page{zoom:…;

4. `oauth21/src/main.ts`：`setupViewportFix()` 在 `app.mount` 之前调用（实测此刻 `.mauth-page` 未创建 → 首帧即正确）。

- 结论：修 `release.mjs` 的 `run()` 需要改代码（异步化 / 换文件型 stdio），**未擅自改动发布基础设施**，
  本轮发版顺延；已把诊断与修法记入 details §9。
- 附带确认：`push | tail` 会把 `$?` 变成 tail 的 → 首次 push **静默失败**（远端仍 8d31806），
  重定向到文件读真实码即成功（8d31806..20d885a）。判据永远以 `git ls-remote` 为准。
