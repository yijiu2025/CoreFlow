## 定位 log.stdout 系统性误用（API 事实已确证，代码未改）

用户报迁移第 3 个文件 `migrations/20260527000001-baseline-all-tables.js` 抛
`TypeError: log.stdout is not a function`。排查后确认这不是迁移独有，而是全仓 CLI/scripts 层的
系统性误用。

### API 事实（源码 + 类型定义 + 运行时探针三方一致）

- `createLogger()` 返回的 `AppLogger` 实例**没有** `stdout` 方法。
  - 原型链：`config / _variant / child / trace / debug / info / warn / error / fatal / time / _emit`
  - own 属性（可调用变体）：`always / dev / prod / file`
- CLI 面向用户裸输出的**唯一出口是顶层导出** `logStdout(text)`（别名 `stdout`），
  定义在 `packages/log/src/index.js:185`，类型声明 `index.d.ts:181`，实现 `transports.js:160`。
  语义：直写 `process.stdout`，无时间戳/级别装饰。
- **不是 API 回归**：`git log --all -S "stdout:"` 与 `-S "stdout ="` 均为空 → 历史上从未存在过该方法。

### 根因

`scripts/migrate-console-to-log.js:62-64` 的 `REPLACEMENTS_CLI`：

```js
log:  'log.stdout',   // ← 错误：应产出 logStdout 调用
info: 'log.stdout',
```

作者的**意图是对的**（脚本第 11 行注释写明"console.log/info → 面向用户的结果输出"），
但目标符号名写错，把 `console.log/info` 映射成了一个不存在的 API。该脚本一次性批量改写了
全仓 CLI/scripts，因此埋下大面积地雷。

### 补充实测：为什么替代品必须是 logStdout 而不是 log.info

同一探针分别设 `LOG_LEVEL=info / warn / fatal`：

| LOG_LEVEL | `log.info(...)` | `logStdout(...)` |
| --- | --- | --- |
| info | 输出 | 输出 |
| warn | **整条丢弃** | 输出 |
| fatal | **整条丢弃** | 输出 |

结论：迁移/CLI 的关键结果输出**必须**用 `logStdout`。用 `log.info` 时一旦 `LOG_LEVEL` 收敛到
warn/error（生产常态），"✅ 已加密 3/3 条" 会被无声吃掉 —— 这是**静默失败**，比抛错更难查。

判定准则：输出给**人**看（表格、进度、结果）→ `logStdout`；给**排查留档**看 → `log.info/warn/error`。

配套改动细节：仅用 stdout 的文件必须**同时删掉 `const log = createLogger(...)`**，否则
ESLint `no-unused-vars` 会报错（13 个文件里有 12 个属于这种"纯 stdout"形态）。

## firewall + Redis 使用优化（20:18-20:40）

用户诉求：「app/firewall，redis 的使用帮我优化，我的 redis 库先学习了解一下，然后使用」。
即先吃透 `src/framework/redis` 的抽象，再用它重写 firewall 的 Redis 访问。

### 核心发现：firewall 的 Redis 用法在真库上**大面积静默失效**

用真实 Redis（192.168.31.19:6379）+ 往返计数探针实测，根因是 **node-redis v5 命令集不兼容**：
- 全小写命令（`hset/hgetall/hdel/zadd/smembers/pttl`）在 v5 里 **全是 undefined** → 抛 `TypeError`；
- `redisClient.pipeline()` 是 ioredis 的，v5 只有 `multi()`；
- `eval(script, numKeys, key, arg)` 旧签名 → "Lua redis lib command arguments must be strings or integers"；
- `scan(cursor)` 传数字 → `"arguments[1]" must be of type "string | Buffer"`。

后果（都发生在生产路径上）：**hash 索引 `fw:blocked:ips` 从未被写入** → 封禁生效但列表永远空、
管理端看不到也解不掉；brute-force / scan-trap 计数整条链路**完全抛错失效**；挑战令牌从未落库；
手动导入把对象当秒数 → NaN TTL 静默失败。

### 做法：新增单一访问层 `src/app/firewall/util/redis.js`

语义化 API + Lua 单往返 + 内存降级 + TTL 归一化，收敛 40 处调用点 / 9 个文件，去掉
`app.redis` / `req.server.redis` 裸客户端在调用链里的传递。往返数实测下降：
`checkGlobalBlock` 4→1、限流窗口 4→1、写封禁 2→1、挑战令牌 2→1、计数器 2→1。

### 顺带修掉的框架级 / 既有缺陷（都用真实 Redis 验证过）

1. **`withTimeout` 孤儿 promise → 进程崩溃**（`framework/redis/utils.js`）：`result.finally(clear)` 派生
   被丢弃的 promise，主 promise reject 时孤儿也 reject → 默认策略下**直接杀进程**。表现是
   「一次 WRONGTYPE 升级为整个服务崩溃」，栈指向 node-redis 解码器。改 `result.then(clear, clear)`。
2. **`getRaw` 返回的是对象不是原始字符串**（我自己的实现与文档不符）：走了会 safeParse 的 `store().get`，
   让 `migrateBlockKey` 的 `raw.startsWith('{')` 抛 TypeError。改用 `store().call(c => c.get(full))`。
3. **CLI 全链路断裂**：`scripts/lib/db.js` 等 5 处仍指向已迁移的 `src/db/`（应为 `src/framework/db/`），
   任何 `npm run cli` 都在第一步就崩；`config.js` 注释里 `HASH_*/LUA_*` 的 `*/` 提前闭合块注释，
   导致 `util/shared.js` **整个文件无法解析**（firewall 加载即语法错误）。
4. **CLI 无法连接 Redis**：`npm run cli` 不启动 Fastify → 插件不执行 → `globalRedis` 恒为 null。
   框架层新增 `connectStandalone()/disconnectStandalone()` 引导，CLI 侧用 `cli/redis-boot.js` 包一层，
   Redis 不可用时**明确拒绝**而不是静默写进程内内存表（一次性 CLI 写内存=写完即丢还打印成功）。
5. **`Retry-After` 从未下发**：`pipeline.js` 两个 `Security Policy Blocked` 回包点只有一个透传 `err.headers`，
   全局封禁阶段漏了 → 客户端拿不到退避信息。补齐并加源码守卫锁「两处对称」。

## 推送 6 个提交到 origin/main（22:59）

`git push origin main` **又一次完全无输出、退出码 0**；`git ls-remote origin main` 显示远端确实已是
`75d3088`（推送真成功），但本地 `origin/main` 仍停在 `7a40b3a`（`git fetch` 还打印了
`7a40b3a..75d3088 main -> origin/main`，纯属谎报）。**根因首次定位**：`.git/refs/remotes/origin/`
目录本身不存在 → git 写松散 ref 失败后静默放弃、也不回填 packed-refs。
`mkdir -p .git/refs/remotes/origin` + 手写 SHA 后 `git status` 立刻恢复正常（松散 ref 优先于
packed-refs 旧值，这次没动 packed-refs）。已把根因与"fetch 那行是谎报"写进 MEMORY.md。

推送后三方 SHA 一致（本地 HEAD = 本地 origin/main = 远端 main = `75d3088`）；
工作区仅剩刻意不提交的 `phonecopy` 孤儿 gitlink。

**更正（同一轮内二次实测）**：上面手写松散 ref 的"修好"**不持久**——紧接着提交记忆并 `git push`，
远端正确前进到 `c58deac`，但本地 `origin/main` 又被打回 `7a40b3a`，且 `.git/refs/remotes/origin/`
**整个目录被删掉了**。机制：git 更新该 ref 时**先删旧松散 ref → 写新值失败 → 清理已空目录 → 回落 packed-refs**。
所以手写松散 ref / `mkdir -p` 只是当场有效，**唯一耐久点是直接改 `.git/packed-refs` 里那一行的 SHA**
（保头行 `# pack-refs with: peeled fully-peeled sorted ` 含尾空格，文件纯 LF）。已按此法改写并确认
`rev-parse` / `show-ref` / `status` 三方一致。**结论：本机每次 push 后都要重写 packed-refs。**
