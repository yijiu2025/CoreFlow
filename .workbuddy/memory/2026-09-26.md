## 核查：URL `?theme=` 在三大设备上的生效机制（答疑，无代码改动）

用户问「链接里写了用哪个主题，手机端可以规定，电脑端能不能也规定」。
结论：**能，机制本来就设备无关**；"电脑端不生效"的表象来自**配色目录差异**，不是机制差异。

### 链路（`src/stores/theme.ts`）
- `readUrlIntent()` 直接读 `window.location.search` 的 `?theme=` / `?skin=`（`?skin=` 是历史别名），
  **刻意不限定设备**，注释原文：「URL 可能来自部署方给电脑端的链接，也可能给手机端。设备匹配留到各调用点（`themeRecordFor`）判」。
- `themeId = ref(urlIntent.theme ?? readInitialTheme())`，且 `urlLockedTheme` 锁定 URL 命中项，后端下发不覆盖。
- 生效与否留给 `getThemeRecord(id, pkg, device, page, view)`：**该设备目录下没有这套配色 → 按"同系别"回落**
  （浅色系选浅色系、深色系选深色系），且回落时**刻意不写** `html[data-mauth-theme]`（避免 DOM 谎报用了某套未生效的配色）。

### 电脑端要扩展主题的做法
1. 新建 `themes/default/<standard|mini>/<page>/colors/<id>/index.ts`，**只写 tokens（`--mauth-*`）即可** ——
   电脑端样式（`stdlogin-*`/`stdreg-*`/`stdforgot-*`）已全 token 化。
2. ⚠️ **不能照抄手机端的 `theme.scss`**：那份选择器针对 `.mauth-page`/`.mauth-body`，电脑端版式类名不同，抄来不命中。
3. 目录名可跨设备同名（`standard/…/blue` 与 `mobile/…/blue` 互不影响，各配各的尺寸/圆角）。

### 两个注意点
- 🔴 **`?theme=dark` / `?theme=light` 是旧语义残留**：`view/web/login/MiniLogin.vue` 的 onMounted 里
  `if (appConfig.theme === 'dark' || 'light') themeStore.applyTheme(...)` 会走"明暗"分支。
  发链接应用**配色 id**（black/white），别用 dark/light。
- URL 可规定的三个参数：`?theme=`（配色，别名 `?skin=`）、`?mode=`（明暗意图 light/dark/system）、`?view=`（版式）。

## 追问：手机端与电脑端要用**不同配色**怎么办（答疑，无代码改动）

### 结论
**机制已支持，且这正是设计意图**（`theme/index.ts` 文件头原文：「同一套设计，手机端用黑白、
电脑端用海蓝是完全合理的诉求……`mobile/colors/` 与 `standard/colors/` 是两个互不影响的
配色集合，虽然目录名可以相同 —— 这正是「手机端、电脑端分别配置主题」的落点」）。

落点 = `themes/<包>/<设备>/<页面>/colors/<id>/index.ts` **按设备各一份**。
`themeId` 是**单一值**（`ref<string>`，localStorage 单键 `STORAGE_THEME`），
但 `themeRecordFor()` 在查询时**带上当前设备** → 同一 id 在两端解析出两份不同记录。

### 已核实的事实
- `default/mobile/login/colors` = black/blue/cyan/rainbow/white；`default/standard|mini/login/colors` = black/white。
- **同名目录确实是两份独立文件**：`mobile/login/colors/black`(109 行) vs `standard/login/colors/black`(116 行)，
  md5 不同、token 集合也不同（standard 版多 danger/warn 等）。
- ⚠️ `mini/login/colors/black` 与 `standard/login/colors/black` **md5 完全相同**（当初是复制而来）
  —— 改 mini 那份**不会**动到 standard，只是现在内容恰好一样。
- 配色是**按页面**各配一份：standard 三页的 black 三个 md5 各不相同。

### 两种「不同配色」要分清
| 诉求 | 是否支持 | 做法 |
| --- | --- | --- |
| 同一 id，两端视觉不同 | ✅ 现成 | 两端各建**同名**目录，各写 tokens（两端都要建） |
| 同一链接，两端用**不同 id**（手机 blue / 电脑 black） | ❌ 不支持 | 需新增"设备维度"URL 参数与 store 槽（见下） |

### 若要做「同一链接、两端不同 id」
现状拦路的三处（都是单值）：URL 只认一个 `?theme=`、`themeId` 单 ref、`STORAGE_THEME` 单键。
改法：`readUrlIntent()` 增读设备专属键（如 `theme.standard`）→ store 存 `Record<ThemeDevice, string|null>`
→ `themeRecordFor()` 优先取「当前设备专属」再落全局 → `setTheme(id, device?)` 分设备落盘。

### 调试面板的能力边界
`ThemeDebugPanel.vue` 的 `deviceOverride` **只切换"预览哪个设备的色卡列表"**（`listColorsOf(device,…)`），
点色卡仍走全局 `themeStore.setTheme(id)`。⇒ 在同一浏览器里**无法**在面板上"给两端分别设"。

### 注意点（与上节一致，补充）
- 「两端不同视觉」时**两端目录都要建**，只建一端 → 另一端按同系别回落，看起来像"没生效"。
- 名字语义：同名 = 同一个颜色概念；若两端是两套**不同品牌色**，给不同名更清晰（如 `ocean` / `standard-ocean`），
  这也让"两端都要海蓝"与"两端各要一套色"在配置上可区分（`theme/index.ts` 原文）。

## 2026-09-26（续）设备维度 URL 参数落地 + 口径收口（已实现，全绿）

### 落地了什么
- **配色侧**：`stores/theme.ts` 的 `readUrlIntent` 支持 `?theme.<设备>` / `?skin.<设备>`，
  链 = 设备专属 → 通用 → 落盘/默认；`deviceTheme` 逐设备记忆 + `urlLockedThemeOf(device)`；
  `setTheme`/`cycleMode`/`toggleTheme` 清**本设备**的 URL 锁，`setMode` 刻意不清（后端/父应用留在 URL 之下）。
- **版式侧**：新增 `theme/views/params.ts`（`readDeviceParam(query,name,device)` / `asThemeDevice`），
  三页容器统一用它取 `?view.<设备> → ?view`；`router/routes.ts` 预取同口径。
- 🔴 **空串 = 未指定（两侧同形）**：版式侧 `isPresent()`；配色侧 `readUrlIntent` 补 `present()`。
  坑：`URLSearchParams.get('theme.mobile')` 对 `?theme.mobile=` 返回**空串而非 null**，
  `'' ?? anyScope` 仍是空串 ⇒ `resolveThemeId('')` = null ⇒ **通用键也被一起吞掉**（与"留空=不特殊指定"相反）。
- `pickRegisterViewId`：补齐「声明档」；删掉重复分支 `if (registerViews.has(url,url,device)) return url`

- `store.viewFor` 从写死 `DEFAULT_THEME_PACKAGE` 改成 `packageId.value`（否则非默认包声明的版式永远读不到）。
- 🔴 **`data-mauth-view` 口径 = 主题包名，且三端每份版式都带**（原来只有手机端 4 份，default 包那三份还写着 `'base'`）。

## 答疑轮（23:04 起，未改代码）

三个口径澄清 + 两个后续项：

1. **默认配色不是单一答案**：`default` 是默认**包**（≡默认版式）；配色有三层 —— 配置兜底 `defaultColorIdOf`
   = 字母序第一 = **`black`**；`syncColorToTone` 里 `standard = dark?'black':'white'` 是**标配对**；
   首屏 `mode=system` + 系统亮色 → 对齐到 **`white`**。所以「看到的是 white、写死的是 black」。
2. **`withViewPreload` 是 `/m/*` 的路由级 `beforeEnter`**：读 `?view.mobile`→`?view` + 读 pkg → `void load()`
   （**不 await**、返回 undefined 放行）→ 与路由组件 chunk 并行下载，容器挂载时多半已缓存。
3. **主题切换 = 参数驱动 + 路由只给设备基线**（不是"依赖路由"）：路由 `meta.device` 给基线、分发器按实际
   渲染形态纠正、`?theme[.设备]`/`?view[.设备]` 定外观、用户操作清 URL 覆盖后走落盘。
   "显式操作 > URL" 是靠**删除覆盖**实现，不是靠排序。

### 🔴 新发现的潜伏缺口（未修）
`routes.ts` 的 `withViewPreload` 传 `{url, pkg, device}` **没传 `theme`**，而容器传 `theme: themeStore.viewFor(page)`
（包声明档）。目前无任何包写 `views:` 声明 → 潜伏；一旦某包/配色声明了版式，预取会算错 id：
白拉一个不用的 chunk、真正要用的仍等加载。修法 = 守卫里补 `theme: viewFor(page, 'mobile')`。

### 抽包可行性（仅评估，未动手）
`src/theme/**` 外部依赖只有 `vue` + `pinia`（无 axios/业务模块），可拆四层：
内核（types/tone/mode/registry/params，纯函数，直接搬）→ 运行时（token 校验注入 + `theme.scss` 装载，需 DOM/存储适配器）

`document.documentElement` + 存储 + `matchMedia`、vue-router（仅 `setupThemeDeviceSync` 与容器读 `route.query`）。
