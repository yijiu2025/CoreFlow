### 教训

- 🔴 **`<details>` 做折叠面板是最省事的选择**：无 JS 状态、无额外依赖、天然键盘可达性。
  配 `summary { list-style: none }` + `::marker` 隐藏即可完全接管视觉。
- 🔴 **折叠 ≠ 藏起来**：组头必须回显关键值（模型名、深度、状态），否则用户得逐个展开才能确认配置。

- **playwright-core 可复用系统 Chrome**（`channel: 'chrome'`），不用下 200MB 浏览器，
  在 CI/沙箱里做版式核验很方便。`boundingBox()` 拿到的是**布局后的真实尺寸**，
  比截图目测靠谱得多 —— 版式重构就该这么验收。

### 🔴 两个教训（都会再踩）

**① 面板可见性判据必须是 `targetSetupOpen`，不能是 `!rootId`。**
我先写成 `computed(() => !store.rootId)`，看起来天经地义 —— 结果「换目标」根本打不开面板：
换目标的那一刻**旧 rootId 还在**（故意不删，用户可能想参考），`!rootId` 恒 false。
而且用户正在标定卡里填结构、还没解析时 rootId 也是空的，那正是最需要看到面板的时刻。
⇒ 一句话：**可见性只归一个显式开关管**；`rootId` 只决定「能不能直接把面板关掉」（守卫用）。

**② 「解析成功」≠「开始分析」，这两个动作必须拆成两个按钮。**
我先让 `setTarget()` 顺手关面板（想少一次点击），结果示例 chip 一点就悄悄收面板开跑，
用户来不及改模型参数。改成：`setTarget()` **不碰** `targetSetupOpen`，
只有标定卡底部的「确定目标，开始分析」调 `closeTargetSetup()` + 第一步 predict。
配套把画板 dialog 里的「解析后自动展开一步」复选框**删掉**（同一个动作两个入口必乱）。
⇒ 落成一行规则：**有副作用的「阶段推进」不能藏在「数据设置」里**。

**③ 「换目标」必须顺手 `reset()`。** 不清旧树会让 TargetInput 的 `seedFromCurrent()` 把旧 SMILES
回填进输入框、`canStart` 误判为可开跑（指向的还是上一个任务的根节点）。

### 🔴 居中：三种做法里只有「脱离文档流」是稳的

标定卡要"整屏居中"，但它是挂在 `.app__content` 里的。我依次试了：

| 做法 | 各视口偏差 | 结论 |
| --- | --- | --- |
| 直接 `justify-content:center` | 恒 +236（侧栏宽） | 基准错：只在主区居中 |
| `transform: translateX(-150px)` | 恒 -64，与栏宽无关 | 数值拍脑袋 ⇒ 修不干净 |
| `margin-right: calc(300px+16px)` | 卡片被压到左边界 x=258 | 反而把可用宽吃掉 |
| ✅ `position:absolute; inset:0` + 外层 `.workspace__layer{position:relative}` | 层内左 70 / 右 70（差 0） | **只有它不随视口漂移** |

⇒ 教训：**要"相对某容器居中"就先让元素脱离那个容器的流向**，
否则它会同时受父级 padding、栅格列、flex 对齐三重影响，逐个补偏移是补不完的。
另外量居中**必须用对基准**：侧栏是常驻导航，基准应是**内容区**（`.workspace__layer`），
拿视口算会被侧栏宽恒带偏 236px —— 这不是 bug，是基准选错了。

### 🔴 别用 `el-empty` 当小占位

### 🔴 本次踩到并修掉的真实缺陷（都是"手写快照"逼出来的）

**症状**：手工构造的 session 快照让整个应用白屏，报
`TypeError: Cannot read properties of undefined (reading 'n1')`，
栈指向 `simulateScheme` ← `schemeStats` ← 计算属性。

**根因链**：
1. 快照从 localStorage 读回来，**可能是旧版本结构**（也可能是用户手改坏的）
2. store 里到处直接解引用结构字段：`rxn.precursorList.join()`、`node.children.forEach()`、

3. 抛在**计算属性**里 ⇒ 控制台只有重复的 promise 报错，很难定位；且整个应用起不来
