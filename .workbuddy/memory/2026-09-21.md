## oauth21 宽屏切电脑版（前端）

**现象**：`/m/login` 在宽屏上不切电脑版；平板横屏 / 折叠屏展开 / 手机开"桌面版网站"时
移动端版式被拉满整屏（用户描述为"页面宽度过宽"）。

**根因**：`utils/device.ts` 的 `detectMobileUA()` 命中即**恒定判定移动端**
（原注释："真机转屏不闪切回桌面版"），视口宽窄完全不参与决策。

**改法**（决策由用户拍定：阈值 ≥1024px；`/m/*` 宽屏**也**跳电脑版）：
1. `utils/device.ts`：新增 `DESKTOP_MIN_WIDTH = 1024` 与 `isDesktopViewport()`；
   判定顺序改为 **宽视口 ＞ 窄视口 ＞ UA**（UA 降为中间段兜底）。
2. `composables/useDeviceDetect.ts`：改为**两个 matchMedia**（min-width:1024 / max-width:767），
   跨阈值实时回调；并在 setup 期先同步算一次（否则真机首帧先按桌面渲染再切，闪一下）。
3. `router/routes.ts`：`mobileRoutes` 加 `beforeEnter: desktopWhenWide('login'|'Register')`，
   **query + hash 原样透传**（授权上下文一个都不能丢）。
4. `assets/styles/mobile-auth.scss`：**一度加了 `max-width: 480px` 限宽，被用户否掉并回退** ——
   限宽会让两侧露出底色，用户明确要求"继续使用拉伸"。**该文件最终未改动**。

**验收**（`.tmp-probe/verify-mobile-width.mjs`，playwright-core + 本机 Chrome，10/10 通过）：
`/m/login` 375→移动端(375宽) / 768→移动端(满宽) / 1024→跳 `/login` 桌面双栏 / 1440→桌面；
`/m/register` 1440→跳 `/register`；显式 `?isMobile=true` 在 1440 仍渲染移动端（最高优先级）；
`/login` 实时缩放 1440→500→1440 = 桌面→移动→桌面（验 matchMedia 响应式）。
`vue-tsc --noEmit` 0 错；改动文件 ESLint 0 问题。

**顺手修掉的坑**：
- `oauth21/src/auto-import.d.ts` 被某次**启动失败**的 `npm run dev` 写成 **0 字节**
  （unplugin-auto-import 生成中断）→ `git checkout HEAD --` 恢复。**启动 dev server 失败后要查这个文件**。
- `oauth21/__tests__/` 下的测试**根本不会被任何 runner 执行**（根 jest `testMatch` 只匹配
  `**/src/__tests__/**/*.test.js`，而 oauth21 workspace 没有 test 脚本）→ 属"死测试"，勿误以为有覆盖。
- `AntiCacheDebugPanel.vue:197` 有一条既有 ESLint 错（`preserve-caught-error`），与本轮无关，未动。

## oauth21 第三轮：拉宽不切换（`beforeEnter` 只在导航时跑一次）

**用户反馈**：`/m/login` 手动拉宽没有自动切换，仍是手机端。

**复现**（`.tmp-probe/diag-resize.mjs`）：375px 进 `/m/login` → 拉到 1200px 后
`path` 仍 `/m/login`、`.mauth-page` 宽度 1200（满宽拉伸）→ 确认未切换。

**根因**：`beforeEnter` **只在导航发生时执行一次**。用户已停在页面上拉宽窗口时
没有任何导航，守卫不会被重新调用 —— 上一轮只验证了"以宽视口直接访问会跳"，
漏掉了"停留页面上视口变化"这条路径。

**改法**：
1. `router/index.ts` 新增 `redirectMobileRouteOnWideViewport()`：挂
   `matchMedia('(min-width: 1024px)')` 的 `change`，跨进宽视口时 `router.replace`
   到电脑版（replace 不改历史，避免"后退又回到 /m/* 再被跳走"的循环）。
2. 判定收敛为单一来源 `resolveDesktopRedirectTarget(to)`（`router/routes.ts` 导出），
   `beforeEnter` 与视口监听共用，杜绝两套标准。
3. 顺带修掉一处**文档与实现矛盾**：文档写着"显式 `isMobile` ＞ 自动识别"，
   而原 `beforeEnter` 完全无视该参数 → 现在显式 `?isMobile=true` 一律不迁移。

**验收**（`.tmp-probe/verify-mobile-resize.mjs`，13/13 通过）：拉宽切电脑版（login/register）、
1023 不切 / 1024 切（边界）、授权参数（`client_id`/`appName`/`redirect_uri`/`state`）原样透传、
`/login` 自身不被改写。

**横屏矩阵**（375 竖屏进入后转横屏）：
| 设备 | 视口 | 结果 |
| --- | --- | --- |
| iPhone SE / 15 Pro Max / S24U 横屏 | 667 / 932 / 891 | 保持移动端（<1024，放不下桌面双栏） |
| iPad mini / Air 横屏 | 1024 / 1180 | 切电脑版 |

**遗留设计问题（用户在评审）**：`/m/register` 与窄屏 `/register` 渲染**同一组件**
（分发器 `view/web/register/index.vue:15` 的 `MobileRegister` 分支指向 `app/register/index.vue`），
实测 375px 下两者文本/元素数一致（66 vs 64，仅多一层 `.login-dispatcher-wrapper`）。
`/m/*` 因此只在 768–1023 段（桌面浏览器窄窗口）有内容级差异；
≥1024 会被跳走，<768 与 `/register` 等价。
其**真实用途**只剩"显式寻址"：`router/guard.ts:35`、`utils/request.ts:158/162`、
`web/auth/Authorize.vue:105` 三处按设备直接跳 `/m/login`，以及 App WebView / 深链的稳定地址。
⚠️ `meta.device: 'mobile'` 是**死元数据**（全仓无读取点）。
另：单向迁移导致"再从宽拉窄 → URL 停在 `/register` 但渲染移动端"的**URL 与版式不一致**。

## 第四轮：手机端布局优化 + 可扩展主题机制（oauth21）

用户诉求原话："手机端页面能不能再优化优化布局，然后怎么可以支持不同主题，扩展以后兼容切换主题等"。
追问后确认三层职责：**用户切黑白** / **开发者（后端下发）换肤** / **组件级 UI 自定义**。

### 一、主题三层 token 架构（`assets/styles/mobile-auth.scss` 711→1006 行）

把原来 99 处裸 hex + 30 个手写 `.dark xxx` 镜像块，重构成三层：

```
① 全局语义 token   --mauth-bg / --mauth-fg / --mauth-cta-bg / …（:root 定义）
② 组件级 token     --mauth-field-bg: var(--mauth-surface)   ← 默认引用①
③ 组件规则         .mauth-field{ background: var(--mauth-field-bg) }  ← 只引用②
```

**明暗 × 皮肤正交**：明暗走 `html.dark`，皮肤走 `html[data-mauth-skin]`，互不干扰。
覆写优先级链（低→高）：`:root` < `html.dark` < `html[data-mauth-skin]` < **inline style**（后端/父应用下发，最高）。
N 套皮肤只需 N+2 个定义块（N 个皮肤 + :root + html.dark），不必 N×2。

⚠️ **重构纪律：深色沿用浅色值**。原文件有些属性只写了浅色、深色没覆写 → 深色下沿用浅色值。
token 化时**逐属性照搬，不"顺手补全"**，否则行为漂移。这是逐像素比对能 8/8 一致的前提。

新增间距节奏 token：`--mauth-pad-header-x/t/b`、`--mauth-pad-body-x/t/b`、`--mauth-gap-cell`、
`--mauth-gap-tabs-bottom`、`--mauth-gap-footer`、`--mauth-logo-size`、`--mauth-title-size`、
`--mauth-field-h`、`--mauth-control-h`、`--mauth-err-h`。矮屏/横屏只调这些，不写第二套布局。

### 三、布局优化四项（全选）

1. **🔴 横屏内容不可达（真实 bug，本轮发现并修复）**
   - 初诊用 `window.scrollTo` 误报"可滚 234px"；改用真实滚轮 `page.mouse.wheel` 测出手势位移 **0px**，
     提交按钮**永远不可见** → 横屏下完全无法登录。
   - 根因：`main.scss` 的 `html,body{overflow:hidden}` 锁死根滚动，而 `.mauth-page` 用 `min-height`
     被内容撑高后，溢出部分被 body 裁掉且无处可滚。
   - 修法：`.mauth-page` 改 `height:100vh; height:100dvh; overflow-y:auto; overscroll-behavior-y:contain;`
     ＋ `.mauth-body` 改 `flex:1 0 auto`（用 `flex:1` 矮屏会被压缩，与外层滚动容器互相挤压）。
2. **键盘不遮挡输入框**：`index.html` viewport 加 `interactive-widget=resizes-content`
   （Android 生效 / iOS 忽略，无害）＋ `useKeyboardAvoid` ＋ `.mauth-cell` 加
   `scroll-margin-top:88px; scroll-margin-bottom:320px`。
3. **留白节奏收紧**：间距全部走 token，矮屏 `@media (max-height:700px)` 只调 token 值。
4. **触摸细节与防穿透**：`.mauth-back-btn`/`.mauth-tab`/`.mauth-checkbox` 用 `::after{inset:-4px}`
   把 36px 视觉按钮扩到 **44px 热区**（不动布局）；按钮加 `touch-action: manipulation`；
   `.mauth-page` 加 `-webkit-tap-highlight-color: transparent` + `-webkit-overflow-scrolling: touch`。

**横屏 header 压行**：`@media (orientation:landscape) and (max-height:560px)` 用 grid 把 header 压成一行。
横屏断点只收紧到字段/按钮 44px 即停（44px 是移动端最小触摸目标，再小违反可用性）。
最终横屏溢出 43px（提交按钮 bottom=391 vs 视口 390）——物理限制，390px 高放不下整套表单。

## 第五轮：主题内容外置成「主题包目录」+ 传参加载

用户追加诉求原话："增加根据传参来加载不同的主题，不一定只能通过后端配置切换主题，后端也可以配置，
可以创建一个文件夹专门放主题，每个主题一个子文件夹，动态加载，主题可能会包含背景图片，边框字体等各种内容的切换"。

### 一、结构：机制与内容彻底分离

```
oauth21/src/
├── theme/                 机制（不因加主题而改动）
│   ├── mode.ts            明暗三态取值 / 循环顺序 / 文案（从旧 themes.ts 拆出）
│   ├── runtime.ts         token 白名单校验 + 分层注入
│   └── remote.ts          后端下发配置拉取
└── themes/                内容（每个主题一个文件夹）
    ├── index.ts           注册表 + 惰性样式加载（import.meta.glob）
    ├── types.ts           MauthThemePackage 契约
    ├── README.md          加主题的做法（三步）
    ├── default/index.ts   默认主题：石墨（**刻意不提供任何 token**）
    └── ocean/
        ├── index.ts      meta + tokens
        ├── theme.scss    背景图 / 装饰条 / @font-face 示范
        └── assets/       wave.svg、wave-dark.svg
```

**加/删一个主题 = 只动 `src/themes/<id>/`**，不碰共享样式表、不碰 store、不碰组件。
（新增目录后需重启 dev server：`import.meta.glob` 是启动时静态扫描。）

### 二、为什么 tokens 同步预载、theme.scss 才懒加载

- `index.ts`（meta+tokens）**同步 eager**：只有几百字节，而 `?theme=<id>` 的合法性校验
  与首帧 `data-mauth-theme` 属性写入**必须在同步路径上完成**，否则先渲染默认色再跳变（闪烁）。
- `theme.scss`（可能内含背景图/webfont 引用）**惰性 `?inline` 动态 import**：这是真正有体积的部分，
  构建切成独立 chunk。实测 ocean = `dist/assets/theme-C1AQQ8-r.js` **1.35 kB**（gzip 0.49 kB），
  且**默认主题首屏完全不请求它**（已用页面请求监听断言）。

### 三、传参加载与来源优先级

| 维度 | 优先级（高→低） |
| --- | --- |
| 主题 | URL `?theme=`（`?skin=` 为旧别名）> 后端 `{theme}` > localStorage `theme-id` > `default` |
| 明暗 | URL `?mode=` > 后端 `{mode}` > localStorage `theme` > 跟随系统 |

两条规则值得记住：
1. **URL/后端命中都不写 localStorage**。它们是"这一侧的默认"，不是用户的选择 ——
   否则「点开过一次带 `?mode=dark` 的链接」会永久改写用户偏好。
   只有 `setMode`/`setTheme`（显式调用）才落盘。
2. **URL 命中的项会被"锁定"**，后续到达的后端配置不得覆盖它 —— 否则入口链接参数形同虚设。
   tokens 没有锁定概念（后端可随时替换整层）。

未登记/非法 id（`__evil__`、`../default`、`Default`、`ocean/../default`、空串）一律忽略回默认，
`resolveThemeId` 只做**精确匹配**不做模糊匹配，避免路径拼装值绕过。

### 四、主题能改什么（用户点名的三类都覆盖）

- **背景图片** → `theme.scss` 里带 `html[data-mauth-theme='ocean']` 前缀写 `background-image`。
  ⚠️ 放在 theme.scss 而不是 token，是因为白名单**刻意拒收 `url()`**（外发请求的唯一入口）。
- **边框** → 走 token：`--mauth-logo-border-width`/`--mauth-logo-border`（已有）＋本次新增
  `--mauth-field-border-width`（默认 `1px`，与重构前 `1px solid` 等价）。
- **字体** → `--mauth-font-family` token（值放行字体栈；字符集不含括号，写不出函数）。
  ⚠️ 落点写成 `font-family: var(--mauth-font-family, inherit)`：**用 var 的 fallback 而不是在
  `:root` 里给具体字体栈** —— fallback 不命中时等价于没写这条声明（font-family 本就是继承属性），
  因此「不启用主题」与「没有这条规则」渲染完全一致，不会引入回归。

### 五、本次修掉的真实 bug（都非常隐蔽）

1. **`styleEpoch` 踩 TDZ → 首屏主题样式静默加载失败**

   在 `watch()` 调用当场同步执行，此时 `styleEpoch` 还未求值 → `++styleEpoch` 抛 ReferenceError

   之后手动切主题都正常 —— 极难从表象定位。修法：把变量与函数声明全部挪到 watcher 之前。
2. **iframe 验收环境失真**（详见 details §10.12）：`@vue/devtools-kit` 在模块顶层无保护读
   `localStorage`；用 `about:blank` 当父页面时 Chrome 禁掉 storage → `stores/theme.ts` 模块求值失败
   → 主题按钮组件 setup 抛错、渲染为空，**与「嵌入判定为真所以 v-if 掉」在断言层面无法区分**，
   会把"应用在 iframe 里已经坏掉"误报成"嵌入行为正确"。改用**真实同站 HTTP 宿主页**（本机 5175）后正常。
3. **视觉比对工具不稳 + 基准自比**（详见 details §10.13）：同代码连拍报 17.8% 假差异；
   `shots-base` 与 `shots-after-run1` 经 `md5sum` 证实是**同一状态** → 早先"8/8 一致"的结论不成立，已重做。

## 第九轮 · 补上两处结构缺口：第三方登录行 + 「保持登录 / 阅读同意」回归

用户指令：「补，提交，保持登录和阅读同意也要在」。三件事：补组件、验收、提交推送。

### 一、先确认「补」的是什么，以及为什么不能做成假按钮

上一轮对照参考图列出的缺口有两处纯主题包做不到：**第三方登录横排图标行**、
**「上次登录」弱提示徽标**。

动手前先摸后端：`api/auth.ts` 里**没有任何第三方登录端点**，全仓也没有相关实现
（`login.third_party` 是"该应用"的占位文案，最初 grep 到它时差点误判为已有能力）。
所以这一排图标**点下去不会真的登录**。于是定了本轮的立足点：

> **providers 为空 → 整行零 DOM。** 有配置才出现。

这不是顺手加的 `v-if`，而是这套能力能安全落地的前提：默认状态下这一行完全不存在，
于是**默认外观零变化，上一轮用逐像素比对得出的回归结论不用重做**（实测 8/8 场景 0 像素差异）。

### 二、能力边界（这是本轮的设计核心）

| 维度 | 优先级（高→低） |
| --- | --- |
| provider 列表 | URL `?social=wechat,qq` > 父应用注入 `window.__MAUTH_SOCIAL_PROVIDERS__` > env `VITE_SOCIAL_PROVIDERS` |
| 授权端点 | 父应用注入 `window.__MAUTH_SOCIAL_ENDPOINT__` > env `VITE_SOCIAL_ENDPOINT` |
| 上次登录 | URL `?lastLogin=` > localStorage 兜底 |

三条硬规则：

1. 🔴 **授权端点只放行站内相对路径**（`/` 开头且非 `//`）。`//evil.com` 是**协议相对地址**，
   浏览器会当成外域绝对地址用 —— 端点一旦能由外部指定，"把用户送去任意外域"就从漏洞
   变成了配置问题，而配置总会被写错。`https://`、`javascript:` 一并拒绝（三例均有验收）。
2. **provider id 做精确白名单匹配**：`__evil__`、`wx`、`qq/../x`、重复项、大小写混杂全丢。
   ID 会被拼进跳转 URL，不校验等于让 URL 决定去哪儿。
3. **未配端点不静默**：明确提示"该登录方式尚未配置授权地址"，而不是渲染一个点了没反应的按钮
   —— 静默失败会被用户当成"功能坏了"，比不显示更糟。

「上次登录」还有个容易写错的地方：**点击不算登录成功**，所以点击时**不写入** localStorage；
写入走 `rememberProvider()`，留给第三方回调真正落地后调用。localStorage 只当兜底
（换设备就没了），外部注入排前面。

### 三、图标：符号而非 logo 复刻

图标用全站一致的 **stroke 风格功能符号**（气泡 / 钱包 / 账号 / 广播 / 分支 / ⌘），
靠**品牌墨色 + 图标下方品牌名**共同表达平台。刻意没有复刻各家官方 logo：
品牌标识的使用需要各自授权，凭空画一个近似版本既可能不合规、也容易画得不像。
正式上线换成授权素材即可，**换图不需要动样式**（颜色由 `--mauth-social-ink-<id>`、
尺寸由 `--mauth-social-size` 控制）。

品牌墨色是**唯一不跟主题变的颜色**（微信绿就是绿）—— 深色下只提亮近黑的 GitHub / Apple
（实测 `rgb(36,41,47)` → `rgb(230,237,243)`），其余保持品牌原色。

### 四、两个坑（都写进了注释与主索引）

1. ⚠️ **徽标只能向上溢出**。`.mauth-page` 是 `overflow-y:auto`，按 CSS 规范另一轴会被计算成
   `auto` → 徽标若横向出界，就会给整页**加出一条横向滚动条**。所以徽标绝对定位在图标
   **正上方居中**（`translateX(-50%)`），行容器用 `padding-top` 留空间，验收里单独立项断言
   横向溢出 = 0。
2. ⚠️ **横屏把图标压到 36px 时热区不能跟着缩**。视觉尺寸降到 36px，热区靠
   `.mauth-social-btn::after { inset: -4px }` 补回 44px（移动端最小触摸目标）；
   相邻 gap 最小 12px，两边各外扩 4px = 8px < 12px，不会与邻居重叠。
   实测三档断点热区 52×71 / 48×67 / **44×62**，最小的那档正好卡在 44px。

### 六、验收脚本自身的一个 bug（值得记）

「阅读同意」那项第一次报失败（`1 → 1`）。真因不在产品，在测试写法：
**Vue 的响应式更新是异步的**，我在 `page.evaluate` 里 `.click()` 完立刻同步读 `class`，
读到的是旧值。改成真实 `page.click` + `waitForTimeout` 后 0→1→2 全对。

顺带发现一个真实交互风险：**点整行中心可能命中协议里的链接**。
`.mauth-link` 的点击是 `stop.prevent`（打开弹窗、不切换勾选），而行中心恰好落在
《服务协议》附近 —— 所以验收改成点 `.mauth-checkbox` 而非整行。
