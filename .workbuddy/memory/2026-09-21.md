## 第二轮：真 Redis 关卡的三个失败点

第一轮修完后 CI 的 **Lint / Test 已全绿**，只剩 Verify 与 Publish Image：

1. **ws-fanout ①「订阅连接未在 10s 内就绪」（退出码 3）**
   `duplicate()` 只复制配置、返回未连接客户端 → 订阅前必须先 `connect()`。
2. **ws-fanout ②「接收端 READY、父进程本地 1 条、子进程收 0 条」**
   订阅回调签名写反成 `(channel, message)`，实际是 **`(message, channel)`**。
   证据：`@redis/client/dist/lib/client/pub-sub.d.ts:11` 的类型定义 +
   `pub-sub.js:336/346` 的 `listener(message, channel)` 实现。
   后果：`JSON.parse('firewall:monitor')` 抛出的 SyntaxError 被 dispatch 的 catch 吞掉，
   **不报错、不留日志**，现象与 ① 几乎一样。
   → 回调改为 `(message, channelName) => dispatch(channelName, message)`，
   补 3 个回归测试，并反向验证（改回旧写法 2 例立刻变红）。
3. **Publish Image 冒烟「等待 /v1/health/ready 返回 200」超时**
   `.env.docker` 的 SESSION_SECRET（30 位）、FIREWALL_SECRET（18 位）低于
   `src/framework/config/env.js` 的 `MIN_SECRET_LENGTH = 32` → 生产模式**拒绝启动** →
   容器反复重启、探针永远 200 不了。→ 改为 CI 里 `crypto.randomBytes(32)` 生成。

**stats-aggregation 与 lock-mutex 本轮已通过**（上一轮把关卡刷写链路改对之后生效）。
复现树本地验收：jest 86 套件 / 1084 用例全绿，ESLint 0 错（18 警告，与基线一致）。
