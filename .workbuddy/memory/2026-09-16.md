### 本轮新增的可复用手法

- **`printRoutes()` 的树形渲染会拆路径段**：`/sessions/devices` 渲染成 `sessions` + `/devices`；

- **503 的真实来源**：`.env` 里 `REDIS_ENABLED=true` 指向局域网 Redis，

  旧测试是纯常量自测从不发请求，所以从没碰到。改造后按「200 或 503」两种真实契约断言。
- **lint 的 `jest/no-conditional-expect`**：分支内 `expect` 会报错。修法是把

## 终端颜色统一 + TTY 自适应（提交 `1233edb`）

用户问「根目录 index 的 `const C = {...}` 是不是不应该在这」——**对，而且比想象的严重**。

### 三层问题（逐层查出来的）

1. **重复定义**：`src/utils/colors.js` 注释写着「全系统统一使用」，已被 **14 个文件** import，
   而根目录 `index.js` 自己抄了一份一模一样的（`reset/green/yellow/red/cyan/dim` 完全同构）。
2. **降级覆盖不全（真 bug）**：`index.js` 里 `IS_TTY` 只用在 2 处（listen、catch），
   另外 4 处裸用 `C.*` —— chcp 失败、关闭超时、已安全关闭、关闭异常。
   **非 TTY 下这 4 处会泄漏 `\u001b[31m`**，而且全是"出错/关闭"这类最需要干净输出的时刻。
   探针实测：非 TTY 下 6 条消息里 4 条含 ANSI。
3. **全仓通病**：`src/` 下 16 个文件、约 86 处裸拼颜色码，**无一降级**。
   `FIX-REPORT-2026-09-15.md:166` 的 🔵-3 曾专门修过 `brute-force.js` 的 3 处，
   说明方向早被认可，只是没修彻底。

### 为什么必须在调用方降级（关键事实）

日志库**只给自己生成的"前缀"上色**（时间/级别/标签，走 `paint()` + `useColor()`），
`transports.js:85` 的 `record.msg` 是**原样拼接**的 —— 消息体里的颜色码完全由调用方负责。
落盘的 JSONL 不受影响（`file-transport.node.js:133` 的 `stripAnsiDeep` 会剥掉）。

### 修法（用户选了"改 colors.js 一处"）

改 1 个文件覆盖全部 16 个使用方 + 86 处调用点：

```js
const IS_TTY = typeof process !== 'undefined' && process.stdout?.isTTY === true;
const code = s => (IS_TTY ? s : '');
const C = { reset: code('\x1b[0m'), green: code('\x1b[32m'), ... };
export { C, IS_TTY };
```

- **改动前先验证前提**：确认没有任何代码依赖 `C` 的字符串值（无 `C[x]` 索引、
  无 `===` 比较、无 `Object.keys(C)`）→ 精搜 `src/` 唯一命中是 `table.js` 注释里的 `ESC[1m` 文字
- `index.js` 的本地 `paint` 随之删除，6 处调用点回到 `C.xxx ... C.reset`，
  与另外 14 个文件**风格完全一致**（一处一套实现比"每处各自判断"更糟）
- 行为验证用**动态 `import()` + query 绕缓存**：改 `process.stdout.isTTY` 后
  `import('./src/utils/colors.js?probe=tty')` 强制重新求值 → TTY 4/4 上色、非 TTY 0/4

四条规则（裸 ANSI 字面量 / 自建颜色表 / 用了 `C` 必须从 `utils/colors.js` 导入 / colors.js 必须 TTY 自适应）

## IS_TTY 收敛：index.js 改为复用 colors.js（提交 `ba356b2`）

用户追问「index 里面的是不是可以移除掉了」——**不能删，但应该改成复用**。

### 判断依据

`IS_TTY` 在 `index.js` 里只剩**一个**真实用途：决定要不要执行 `chcp 65001`。
这与颜色**是两件事**：

- 颜色问题 → `chcp` 无关，已由 `colors.js` 按 TTY 降级，直接插值 `C.xxx` 即可
- `chcp` 改的是**终端代码页**，属"非颜色类的终端能力判断" —— 无终端的进程执行它是无意义的

所以正确做法是保留判断、但**复用** `colors.js` 已导出的 `IS_TTY`，
而不是删掉整段（删掉会导致 docker/pm2 里也去跑 chcp）。

### 改动前的验证（必须先做）

两处判断写法其实**不同**，需确认等价才敢替换：

```js
index.js  : process.stdout.isTTY === true
colors.js : typeof process !== 'undefined' && process.stdout?.isTTY === true
```

探针在 `true` / `undefined`（管道）/ `false` 三种取值下对比 → **三者取值完全一致**，可安全复用。
（差异只在浏览器/无 process 的边缘环境，Node 服务端入口恒等价。）

### 结果

- `index.js`：删本地读取，改 `import { C, IS_TTY } from './src/utils/colors.js'`，
  悬空的 JSDoc 改写成挂在 `chcp` 段上的行注释（解释"为什么这里用 IS_TTY 而非颜色开关"）
- `colors.js`：文档补充 `IS_TTY` 的导出用途
- **全仓 `process.stdout.isTTY` 读取点：2 处 → 1 处**（仅 `colors.js`）

### 守卫加第 5 条规则

「TTY 判断只允许出现在 `utils/colors.js`，其它处须 `import { IS_TTY }`」
+ 第 4 项反例（**含"注释里提到 isTTY 不算违规"** —— 先剥块注释/行注释再匹配，
否则本测试文件的说明文字会自己把自己判违规）。

- 覆盖范围扩到**项目根**（`collectRootScope()`），因为 `index.js` 在 `src/` 之外
- 植入 `const _PLANTED_TTY = process.stdout.isTTY` 实测 → 精确报出该规则失败 → 撤销恢复

验证结果：全量 **60 套 / 872 项通过**（+2 项即新增的两条规则），ESLint 0 problems。
