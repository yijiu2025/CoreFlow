### 🔴 三个决定性踩坑（下次照抄即可避）
1. **机器码必须只由 MachineGuid 决定**。最初掺了卷序列号(`GetVolumeInformationW`)

3. **入口不能走 `runpy.run_path`**。它用临时命名空间，`sys.modules['__main__']`

### 第三十八轮：路线「手动绘制修改部分路线」前期勘察（仅分析，未动代码）

结论：**可行、后端零改动**。本质不是"画一张图"，而是**给某个节点换一组前体** ——
因为树已经把"这一步怎么做"抽成了 `MolNode` 上的候选反应（`node.chosenReactionId`），
而 `Reaction.id` 由 `reactionIdFor(nodeId, precursors)` 确定性派生（workspace.ts:71）⇒
手工造的反应与模型给的反应**同构**，天生兼容 `RouteScheme.choices` / `adopt` /
`applyScheme` / `simulateScheme` / `childrenOfReaction`。

最小原语只有一个：`setPrecursors(nodeId, precursors[])` → 造一条 `origin:'manual'` 的
Reaction 塞进 `node.candidates` → 走现成的 `adopt()`。三类操作都是它的组合：
①改前体 ②加/减组分 ③插入中间体（= makeNode 一个 X + 把父反应前体里的 P[i] 换成 X，
再 adopt）。

🔴 **五处必须同时改，否则静默坏**（勘察结论，开工前先看这几行）：
1. `normalizeNode`（:1582）`typeof r.probability === 'number' ? r.probability : 0`
   ⇒ 手动步若用 `null` 表"无概率"，**从 localStorage 恢复后会被写成 0**，连乘直接归零。
   要么把 `Reaction.probability` 改成 `number | null` 并在这里兜 `null`，要么别用 null。
2. `pushRun`（:544）`merged = [...run.candidates]` ⇒ 重新分析会**冲掉手动候选**
   （现在只捞回 `chosenReactionId` 那一条）⇒ 手动候选必须显式 filter 回来。
3. 连乘点两处要跳过手动步：`adopt`（:1027 / :1042 的 `probabilityChain`）与
   `simulateScheme`（:1900 的 `prob *=`）。
4. `copyAnalysis` / `reuseSiblingAnalysis`（:605/:629，走 `materializeCandidates`）
   会把**别处同分子的手动候选一起复制过来**（id 会重算，行为上算特性但要给「手动」徽标）。
5. 插入中间体：**必须先算出新 reactionId、再 makeNode X 并设 `parentReactionId = 该 id`**，
   否则 `adopt` 里 `childrenOfReaction(reaction.id).find(n => n.smiles === smi)` 找不到 X，
   会**重造一个重复节点**。

天然正确的部分（不用管）：`currentSchemeConflicted`（:1742）判据是"方案里记的那一步现在对不上"

## 追加（同日晚）：找到「多步拆分没结果」的**真正根因** —— 搜索预算被历史调用吃掉

上面那三条是**观感层**的原因，都**不是**根因。真正的根因：

🔴 **`should_stop_search` 比的是 `reaction_model.num_calls() >= limit_reaction_model_calls`，
而 `num_calls()` 返回的是「缓存未命中**累计数**」，只在 `reaction_model.reset()` 时归零。**
官方 CLI 每次搜索前都 `alg.reset()`（`syntheseus/cli/search.py`），**我们漏了这一步**；
而改造后模型是**常驻**的（`web/model_server.py`）⇒ 这个计数从加载那刻起**跨搜索一路上涨**，
涨过 `max_calls` 之后**每次搜索开局即停**。

**入口线索是「0 秒」**：`max_calls=40/60/80` 一律 **0.0~0.1 秒**返回、`routes=0`、
`stats={or_nodes:1, and_nodes:0}`（根节点一次都没扩展）；`max_calls=120` 才跑得动
（122s / or_nodes≈2900）。⇒ **0 秒说明搜索根本没启动，跟「预算不够所以没找到」是两件事。**
上面那组「40 calls 出 8 条路线」的实测数字，正是在**模型刚加载、计数还小**的窗口里测到的
（**幸存者偏差**）；同一参数跑过几轮之后就是 0 秒 0 结果。

**改动（都已验证）**
- `web/model_runtime.py` + `scripts/search.py`：`limit_reaction_model_calls = model.num_calls() + max_calls`
  （=「当前基线 + 本次预算」；不 reset 是为了保留跨搜索 cache）。
  验证 `.tmp-probe/verify-calls-budget2.py`：**stop → start 真重启**后连跑 3 次 `calls=40, ha=10`
  ⇒ **65.6 / 60.1 / 60.3 秒、各 5 条路线、or_nodes≈1530、0 次早退**（修复前同参数 3 次全 0 秒）。
  ⚠️ 修复住在**模型服务进程**里（`run_retro_search` 在那边执行）⇒ **必须重启模型服务才生效**。
- `web/model_client.py` + `web/app.py`：`load(force=...)`，`restart` 走 `force=True`。
  原来 `restart` 在「模型已就绪」时是 **no-op**（`already: true`），返回体照样 ok，**完全看不出来**
  —— 本轮排查被它坑了一整轮（以为新代码生效了，其实还在跑旧进程）。
  验证 `.tmp-probe/verify-restart-force.py`：替身覆盖 `status/stop/_spawn`（不碰真服务）8 条 ALL PASS；
  **反向证明**去掉 `not force` ⇒ **恰好 3 红**（force 分支那三条）；装回复跑全绿。
  ⚠️ 需**重启 API 进程**生效。
- 前端四关全过：`vue-tsc -b` 0 / `eslint` 0 / `npm run test:store` ALL PASS /
  `vite build --outDir .tmp-probe/build-verify-1` exit 0。

**顺带量清的重原子阈值口径**：界面 `heavyAtomThreshold=6` 是**故意**的（`DEFAULT_PARAMS`
注释有理由：阈值 10 会让阿司匹林一步到底、「多步」形同虚设），而后端三处默认都是 **10**。
利多卡因 `C14H22N2O`（17 重原子）：**阈值 6 + 120 calls 跑 126 秒仍 0 条**
