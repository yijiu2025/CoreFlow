### C. 🔴 修掉 `run_api.py` 的 spawn 缺陷（本轮最重要）
上一轮我继承了 `exec(compile(src), {"__name__":"__main__"})` 写法，**它会让 Windows
multiprocessing spawn 直接崩**：
`PicklingError: Can't pickle model_worker_main ... on __main__ failed`。
根因：spawn 子进程按 `sys.modules['__main__'].__file__` 重载主模块找 worker，只 exec 不注册
⇒ `sys.modules['__main__']` 仍是 run_api.py，找不到 worker。
修：`types.ModuleType("__main__")` + `__file__` 指 `web/app.py` + `__spec__=None` +
**注册进 `sys.modules`**，再 exec 到 `main_mod.__dict__`。
**对照实验**（`.tmp-probe/verify-spawn.py`，假 app 内含 spawn）：注册 → `SPAWN-OK: child-alive`；
只 exec → `exit=1` + `PicklingError`。⇒ 🔴 **规则：凡"代跑 app.py"的启动器，必须注册 `__main__`。**

## 第四轮：Ketcher 画板落地（用户拍板走 npm `ketcher-react`）

### 背景

用户拍板：「**编辑器用 Ketcher**」→「**npm 引 ketcher-react**」。本轮做完。

### A. 从产物里读出来的三条硬事实（没跑起来就别猜）

工具：`.tmp-probe/probe-ketcher-wasm{,2,3,3b}.mjs` —— 把 `ketcher-standalone/dist/main.js`
里的内联 base64 worker 解出来再 grep。

1. 🔴 **wasm 不是外部文件，是内联 data URI。**
   worker 里 `findWasmBinary(){var f="data:application/octet-stream;base64,AGFzbQEAAAAB…"}`
   —— 8.9MB Indigo WASM 以 base64 塞在 12,130,285 字符的 worker 源码里，worker 本身由
   16,173,716 字符的 base64 再包一层（顶层 `main.js` 因此 **16MB**）。
   推论：`staticResourcesUrl` 传空串即可；**不可能**出 wasm 404 / 相对路径基准错（worker 是 `blob:`）；
