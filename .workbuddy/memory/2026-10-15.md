## oauth21 Vite 工程化优化（代码分割审查 + 预算守门 + 部署方案）

- **背景**：用户要求对 oauth21 做 Vite 工程化优化（代码分割/懒加载/资源压缩）+ 调优方案与指标。结论先行：**路由懒加载、manualChunks 分包（vue/form/net 三组）、dropConsole（Vite8 Rolldown 口径 `rolldownOptions.output.minify.compress`）、sourcemap:false 早已就位**，无需重构。
- **本次实改**（6 文件）：
  1. `index.html` favicon 断链修复：`/vite.svg` 是模板残留、public/ 无此文件 → SPA fallback 吃成 index.html（图标静默失效 + 白背 1.8KB）。改指 `/favicon.svg`。
  2. `vite.config.ts`：`build.modulePreload.polyfill: false`（原生支持 Chrome66+/Safari16.4+；不支持的要么跑不了 ESM、要么只损预加载加速）。**不设 target**——Vite8 默认已是 `baseline-widely-available`，写 es2020 反而更宽。
  3. `public/favicon.svg` 安全子集压缩 -9%（9,522→8,710B）：删默认值 fill-opacity、删与 style 重复的 presentation attr、小数按量级降精度。
  4. 新增 `e2e/verify-bundle-budget.mjs`（已接入 verify-all 静态组 + VERIFY.md，活跃关卡 21→22）：对**落盘真实字节** `gzipSync(level6)` 自算，预算线 = 首屏静态集 gz≤150KB（实测135.6）/文件数≤12（8）/单chunk gz≤60KB（51.4）+raw≤200KB（160）/dist≤1MB（808.5）/index.html≤8KB（2.8）。自带 `--poison` 毒丸自证（预算归零必须全红，实测 exit=1）；无产物 exit=3。**改预算线=显式决策，必须同步文件头基线注释**。
- **实测数据**（生产构建 + preview brotli + SW 屏蔽）：窄屏 /login 首屏 47 请求/211.0KB 过线；宽屏 43/207.9KB；**拉宽/缩回增量 0 请求**（三形态预热的设计回报，e2e A1 断言，勿为省 19KB 破坏）；form-vendor 51.4KB gz 是首屏唯一大头（vee-validate useForm + zod4 核心）。
- **两个"分析后刻意不动"**（防后人重复踩）：① `useQrLogin` 静态引入保持——onMounted 有 `hasAppName→generateQR()` 自动生成，动态 import qrcode 只推迟几毫秒还多一层瀑布，总流量不变=负优化；② 不拆 form-vendor——首屏表单校验两者都要，拆分只加请求数。
- **🔴 血泪教训：SVG 压缩无脑 `round(v,2)` 会把 `matrix(.00324 …)` 的微缩放因子归零** → 装饰椭圆压扁、G 通道最大差 27/255 肉眼可见。自适应精度：|v|≥0.1 留 2 位、<0.1 留 4 位。视觉验证必须做**同文件渲染两次的对照**（排除 Chrome 渲染噪声）+ 看 Δ 分布（本次 99.99% 像素 Δ≤7 才放行）。
- **方案文档**：`oauth21/docs/frontend/performance-tuning.md`（LCP≤2.0s/INP≤200ms/CLS≤0.1/TTFB≤300ms 指标表 + nginx brotli/immutable 缓存/no-cache 例外（index.html+sw.js）完整片段 + 深水区：vee-validate 轻量化 -35~45KB gz > axios 替换 -15~18KB > CSS 拆细）。
