## 🔴 删除元凶定案（受控复现实验，4 轮）

- **元凶 = WorkBuddy 自带沙箱的文件备份/回滚子系统**（`D:\Program Files\WorkBuddy\resources\app.asar.unpacked\cli\vendor\sandbox\5.5.5\`，
  进程 `sandbox-cli-gc.exe`/`sandbox-cli.exe`/`sandbox-center.exe`，日志 `~/.workbuddy/logs/sandbox/<日期>/sandbox_gc_*.log`）。
- **受控复现**：`git rm` 仓库根部文件 → 无事；`git rm` **src/ 内**的跟踪文件 → src 全目录（415 文件）
  在 ~12s 内被级联删除，稳定复现 2 次；`rm` + `git add -A` 删除同文件 → 无事。
- **gc 日志实锤**：删潮分钟内 sandbox-core watcher 连续记录 341 条 `11.d.*`（deleted）备份条目，
  与真实文件消失逐秒吻合；`11.m/11.d/11.a.*` 是它的修改前备份索引（modify_backup，总量 ~700MB）。
  推断：git rm 的删除事件触发其回滚/对账逻辑异常级联，把整个备份索引当删除清单执行。
- **规避（已验证）**：本仓**永远不用 `git rm`**；删除一律 `rm <file>` + `git add -A`；
  恢复一律 `git checkout HEAD -- <path>`（从不触发）。
- 附带发现：`git rm` 中途 SIGTERM 会留 0 字节 `.git/index.lock`，需手动删（先确认无 git 进程）。
- 这是 WorkBuddy 产品缺陷，建议带日志反馈；监视器 `.tmp-probe/watch-src.mjs` 保留作保险。

### 核心诊断（本方案与"再加一堆规则"的本质区别）

问题**不是"没人审查"，而是审查没有分层**，导致三种失效同时发生：
规则入口七零八落（同一条"导出放末尾"散在 eslint / 守卫 / 文档三处）、
本地闸门被关闭、**已有文档在说谎**。故第一原则：
**能自动化的绝不写进人工清单；写进人工清单的必须是机器结构上抓不到的东西。**

分级用「爆炸半径」而非主观严重度：L0 阻断 / L1 整改 / L2 建议 / **L3 风格由工具负责，明令禁止人工提出**。
