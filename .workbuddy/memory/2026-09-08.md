# 2026-09-08

## 设备 ID 登录态恢复（device.js / session.js / auth index.js）

- 新增 `session_tokens.device_id_original` 字段（迁移 `20260908000001`）：首次登录原始设备 ID，写入后永不更新；存量行回填 `device_id_original = device_id`。`device_id` 保持"当前最新"语义（人机验证通过后由 `updateSessionBaseline` 及时写回，原本就有）。
- `getDeviceId(request, opts)` 新增步骤 1.5：header+cookie 均无有效 ID 时，优先从 Redis `sessionData.deviceId` 恢复，旧会话缺失才走 `loadFromDb` 回调查 `session_tokens`（device_id 优先、device_id_original 兜底）。恢复带设备类型兼容校验（`detectDeviceType` 粗粒度比对，防 sid 被窃后跨环境继承受害者身份；UA 大版本变化不误伤）。
- `index.js` 认证钩子传入 sessionDeviceId/sessionUserAgent/loadFromDb；恢复后靠已有的 X-Device-Id + Set-Cookie 回写收敛到前端。login.service / verify-challenge / token-issuer 调用点不变（向后兼容）。
- 关键设计约束：恢复目标必须与风险基准指纹同源（登录链最新 ID），不能用原始 ID 恢复，否则指纹比对必失配→风控误报死循环；原始 ID 只做审计+兜底。
- 测试：device.test.js 新增 9 个登录态恢复用例，framework/auth 全部 52 测试通过。

## 设备 ID 丢失/变更弹人机验证（与指纹变更同级）

- `index.js` 认证钩子传入比对结果（resolved deviceId vs 客户端上报 header||cookie）。
- `verify-challenge.js` 修复：getDeviceId 补 loadFromDb 恢复参数——否则客户端无 ID 时验证端点会随机生成新 ID 更新基准，免验标记失配 → 反复弹验证死循环。
- 行为变化：原「cookie 兜底恢复/登录链恢复」是静默无感收敛，现在恢复成功也会 warn 弹验证一次（用户要求：身份丢失本身即异常）；验证通过 + X-Device-Id 回写收敛后不再弹。
- framework/auth 测试增至 58 个全过。

## getSession DB 降级路径修复（session.js）

- Bug1（严重）：TTL 判定锚点由 `token.createdAt` 改为 `token.last_active`——session_tokens 行按 (user_id, device_id) 幂等复用，re-login 不更新 createdAt，导致行建行超 30min/30d 后 Redis 降级路径误判（刚发的 sid 被清/误 revoke）。
- Bug2：指纹补取的按 device_id 再查是冗余的（模型有 device_fingerprint 且行幂等复用，查回的就是同一行），改为直接读 `token.device_fingerprint`，省一次 DB 查询。
- 已知未修（提示过用户）：DB 重建的 sessionData 缺 familyId（模型无该列）→ sid_r 轮转盗用检测降级为孤儿 family 单 token 撤销；Redis 命中路径返回 accessCount、DB 重建路径不返回（无实际影响）。根治 familyId 需给 session_tokens 加 family_id 列。

## detectLoginAnomaly 改走统一存储层

- 澄清：`request.server.redis`（=app.redis）与 getStore 用的 `globalRedis` 是同一个 node-redis 客户端，全项目只有一条主连接，不是两套 Redis。
- 缺陷：detectLoginAnomaly 收裸 redis 客户端直接 get/set——Redis 故障时 app.redis=null → 锁定逻辑静默跳过（最需要防护时失效）、无超时保护、无命名空间。
- 修复：改用 `getStore('login_lockout', {timeout:3000})`（Redis 故障降级 MapStore 单机兜底），clearAccountLock/clearIpLock 同步去 redis 参数，login.service 调用点删 `redis` 字段。旧 lockout key TTL≤30min 自然过期，无兼容问题。
- 未动：audit-logger 的 lPush/lTrim（getStore 未封装 list 操作，DB 是主存储、Redis 层 try/catch best-effort，影响小）；firewall 大量直接用 app.redis 的 pipeline 等高级命令属历史架构。

## detectLoginEnvironmentAnomaly 多设备基准 bug 修复

- 原逻辑取"全局最近一条未吊销 session_tokens 行"当唯一指纹基准：行按 (user_id, device_id) 幂等且 re-login 只更新本次设备行 → 两台已验证设备交替登录永远互踩指纹，每次换设备都误弹邮箱二次验证
- 多 app 同理：不同域的 device_id cookie 不同 → 同一物理设备多行多指纹，"最新一条"可能来自另一 app
- 修复：改为"任一未吊销行指纹匹配即已知设备 → safe"，无匹配才取最新行区分首次登录/环境变化；IP 只与匹配到的那行自身 IP 比；排序加 id DESC 保稳定
- 安全性不降：已知设备都至少通过过一次邮箱二次验证；新设备/盗号者无匹配 → 照样 warn
- 新增 6 个测试用例（已知设备 safe、新设备 warn、首次 info、IP 漂移 info、基准缺失 info、FORCE 开关），framework/auth 64 测试全过

## device_id vs 指纹匹配分析 + platformHint 不一致 bug

- 用户问 known-device 匹配该用 device_id 还是 device_fingerprint → 结论：保持指纹。device_id 值可经 localStorage 被 XSS 读取、x-device-id header 客户端可控，知道值即可在任意机器冒充；指纹绑定 UA，冒充者 UA 不同 → 匹配失败仍 warn。成本是浏览器大版本升级后首次登录要验一次（验证后行内指纹刷新）
- 排查中发现更严重 bug：指纹材料各调用点不一致——createSession 存基准 platformHint=''，detectLoginEnvironmentAnomaly 却传 detectPlatform(request)='web' → currentFp 永远匹配不上库中指纹 → 每次密码登录误弹邮箱验证。已修：登录链指纹统一不含 platformHint（认证钩子/verify-challenge 本来就没传，|| '' 归一）
- 新增防回归测试：手工按 createSession 材料（deviceId|uid|UA|）拼指纹作 DB 行，不与被测函数共用计算入口，材料漂移立即失败
- 教训：测试桩与被测代码用同一函数算期望值时测不出材料漂移——期望值要独立构造
