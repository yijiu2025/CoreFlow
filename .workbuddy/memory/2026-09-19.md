### 核心结论

**分层设计本身健康，不应推倒重来。** 阻碍扩展性/稳定性的不是分层，而是三类可定点修复的问题：

- **A 类｜单实例假定被硬编码进三个子系统**（防火墙遥测 / 定时任务 / 运行时配置）
- **B 类｜文档·代码·配置三者不一致**（文档承诺的能力在代码里完全不存在）
- **C 类｜启动期失败语义不明确**（有的静默降级、有的 fail-fast，无统一判据）

关键判断：**A 类解决前，加机器不但不提升容量，还会让防火墙统计、限流阈值、定时任务行为全部错乱。**

### 0.3 的最大发现：报告初稿方案经实测部分不成立

初稿建议 `forceCloseConnections + keepAliveTimeout + requestTimeout + connectionTimeout`。逐项实测：

| 选项 | 实测结果 | 处置 |
| --- | --- | --- |
| `connectionTimeout` | **空旋钮**：传入后 `server.connectionTimeout` 为 `undefined`、socket 上无计时器；建连后发任何字节 10s 也不断开 | **不设** |
| `headersTimeout` | 被 Fastify **静默丢弃**（选项校验对 schema 外键是 removeAdditional 语义）；慢 header 由 Node 内建 60s 兜底 | 不设 |
| `keepAliveTimeout: 72000` | 这是 Fastify **默认内置值**，显式声明 = 零行为变更 | 显式声明（可 env 覆盖） |
| `requestTimeout` | Fastify 默认 **0（关闭）**；显式打开用于封慢速发 body（RUDY）——防火墙 6 个检测器里无慢连接检测，这是唯一防线 | 设 300s（给 200MB multipart 余量） |
| `forceCloseConnections: true` | 对**普通 keep-alive 连接**有效（close 从"等超时"变 1ms 返回），但对**已 upgrade 的 WebSocket 连接完全无效** —— `closeAllConnections()` / `closeIdleConnections()` 后 `server._connections` 仍为 1、`close()` 回调不触发 | 设上（管住普通连接），WS 另修 |

**真正瓶颈是 WS 半开连接**。`@fastify/websocket` 11.2.0 默认 `preClose` 只 `client.close()` 等对端回应
→ 半开连接让 `app.close()` 永不返回。修法：自定义 `preClose`（`src/framework/websocket/preclose.js`）
= 广播关闭帧 `1001 going away` → 宽限期（默认 1000ms，unref 定时器）后 `terminate()` 残留 →
`wss.close(); done()` **立即返回**（不与 `wss.close()` 回调耦合，解卡靠 terminate）。
只有 `socket.destroy()` / `ws.terminate()` 能解卡，这是实测结论。

### 1.1 健康探针：一个报告未识别的连带风险

实现 `/v1/health/live`（恒 200）+ `/v1/health/ready`（关键依赖不可用返 503）+ `/v1/health`（兼容恒 200）。
两条关键判据：
- **只有"已配置"的依赖参与判定**：`REDIS_ENABLED!=true` 时访问层走进程内 MapStore 降级，是**合法模式**
  而非故障，判成 not-ready 会误摘流。
- **探测必须带超时（3s）**：DB 连接池枯竭时 `sequelize.authenticate()` 会等到 `pool.acquire` 超时（默认 30s），
  编排探针自身超时通常 1~5s → 会被自身超时掐断、掩盖根因。

⚠️ **实施中才发现的新风险**：探针被自家 Bot 检测拦截。`shouldSkipDeepCheck` 原本只豁免挑战验证接口
+ 静态资源；探针通常**不带 User-Agent**（Docker HEALTHCHECK / 自研监控）→ 命中 `checkBotChallenge`
的 `requestCount > botChallengeNoUaLimit`（默认 10）→ 60s 窗口 5s 一次 = 12 次 → 返回**挑战页 HTML 且 200**，
探针"看起来通过却完全失效"。修法：`engine/pipeline.js` 加 `PROBE_PATHS` 豁免名单（三个探针路径）。

### 1.2 启动失败分级（本轮主要改动）

`engine.js` 原先只有 `DUPLICATE_ROUTE` 会终止，其余全部降级成 warning → 「服务在跑但功能缺失」
（鉴权没装、路由没注册，进程却健康监听端口，故障伪装成 404/500）。

改法：**显式声明可降级者，未声明即关键**
- `OPTIONAL_LOADERS` = 01-monitor / 02-redis / 03-db / 09-notice，每条注明可降级理由
- 未列入者失败 → fail-fast，且**默认取"关键"是有意为之**：新增加载器忘了声明时会拦住启动，
  而不是被静默放过（反向缺省会让"漏声明"变成安全漏洞）
- fail-fast 前先 `reportLoadErrors(loadErrors)`，否则已收集的可降级错误会被这次抛出吞掉
- 抛出的错误带 `loaderFile` / `loaderCritical`，上层日志能直接指出是哪个文件拦住启动

关键判据（判"可选"的依据）：**该模块缺失后服务仍能正确处理已注册路由的核心请求**。
`03-db.js` 之所以可选，是因为它自身的语义就是"连接失败不阻塞启动，降级为 null"（文件头写明）；
`02-redis.js` 可选是因为未配置时走 MapStore 降级是合法模式。

### 顺带修掉一个信息泄露

`/health/ready` 是 `requireLogin: false` 的**公开**端点，而原实现把它当作内部接口写着 ——
`detail: err.message` 直接把 `sequelize.authenticate()` 的报错回显出去，实测形如
`connect ECONNREFUSED 10.0.0.5:3306`，**等于对外提供一张内网地图**。
改为 `errorLabel(err)`：只取 `err.code || err.name`（如 `ECONNREFUSED`），完整错误进日志。

> 教训：写探针时容易只关注"能不能反映状态"，忘了探针往往是**整个服务里最公开**的端点。
> 新增任何进出 body 的字段，都要先问一句"这东西给未登录的人看合适吗"。

### /health/ready 的 loaders 语义

有可降级加载器失败时 → `status: 'degraded'` 但**仍 200**。
理由：加载器降级不等于不可服务，判 503 会让编排系统摘掉一个还能正常处理请求的实例。
（关键加载器失败则进程根本起不来，探针无机会响应，所以这个字段永远只会显示可降级项。）

### 新增手法：用 fixture 目录驱动「动态 import」类代码

`engine.js` 内部是 `await import(pathToFileURL(file))` —— **`unstable_mockModule` 对它无效**
（mock 注册的是模块说明符，不是运行时拼出的 file URL）。
解法：给被测函数开一个 `options.registryDir` 参数，测试用具名 fixture 目录喂进去，
**走的是与生产完全相同的「读目录 → 排序 → 逐个 import → 调 register」路径**，
只是目录内容可控。比 mock 更接近真实，也顺带覆盖了排序与目录扫描逻辑。

配套的 fixtures 放在 `src/__tests__/__fixtures__/`：

- `loader-ok/`（00-globals 成功 + 01-monitor 抛错）→ 验证可降级
- `loader-critical-fail/`（08-api 抛错）→ 验证 fail-fast
- `loader-unknown-fail/`（99-unknown 抛错）→ 验证"未声明即关键"

> ⚠️ fixtures 目录必须放 `src/__tests__/` **里面**（jest 的 `testMatch` 是
> `**/src/__tests__/**/*.test.js`，只匹配 `.test.js`，所以 fixtures 不会被当测试文件）；
> 若放到仓库外（如 `os.tmpdir()`），会因为不在项目 `"type": "module"` 作用域内
> 而被当 CommonJS 解析，`export default` 直接语法报错。

## 发版自动化升级（同日晚，用户要求"tags、release、package 要按情况自动发布"）

上一段的结论**有一半是错的**："本机无 gh CLI 所以不建 Release" —— 缺的是**工具**，不是**权限**。
GCM（git credential manager）里存着 GitHub OAuth token（`gho_` 前缀，scopes `gist/repo/workflow`，
账号 `yijiu2025` 对本仓库 admin）。`git credential fill` 取出来直接调 REST API 即可，**无需装 gh CLI**。

### 三条通道的能力与判据

| 通道 | 何时发 | 凭据 |
| --- | --- | --- |
| git tag | 判定发版即打 | git 自身 |
| GitHub Release | 与 tag 一一对应 | GCM 里的 OAuth token（`git credential fill`） |
| npm（`packages/log`） | 该包本地 `version` **已 bump 到高于线上** | `~/.npmrc` 的 authToken（已登录 `qirly`） |

npm 那条判据的由来：`packages/log` **没有任何 tag**（只能以 version 作基线）；version 相等即视为
"无发布意图" —— 这正是 npm 的语义（版本号本身就是发布凭据）。

### 落地

`scripts/release.mjs`（宿主）+ `src/framework/release/index.js`（纯逻辑）。

**逻辑必须下沉到 `src/`**：约定禁止 `src` import `scripts`（守卫 `no-scripts-import.test.js`），
而 jest 只收 `src/__tests__/**` → 逻辑若留在 `scripts/` 下**等于无法测试**。这也延续了既有先例
"CLI 工具库已迁到 src/framework，scripts/lib 不再持有副本"。默认 dry-run，`--apply` 才执行；
`--from <ref>` 用于复盘/补发；`--allow-dirty` 供并行任务占用工作区时使用。

### 实测坑（均已写进测试）

1. **破坏性变更判定不能退化成子串匹配**。commit 正文里"提到"该关键词（正是我在写这条规则时
   提到的）会被当成真声明 → 把 minor 误升成 major。**本仓库真实发生过**：`--from v2.5.0`
   一度算出 `v3.0.0`。收紧为只认 Conventional Commits footer 形式（行首 + 冒号）后恢复 minor。
   反例测试已钉死，毒丸复验精确命中（正好该项变红）。
2. **Windows 下 `execFileSync('npm')` 直接 ENOENT**（npm 实为 `npm.cmd`），指定 `'npm.cmd'`
   又 EINVAL，**只有 `shell: true` 可用**。查线上版本因此改走 registry HTTP 接口。
3. **eslint flat config 的 `**/*.js` 不匹配 `.mjs`** → ESM 脚本拿不到 Node globals，
   `process` / `fetch` 全报 no-undef（既有 `scripts/cleanup-users.mjs` 同样中招，只是从没被 lint 到）。
4. **首次真实发版暴露了脚本自身两个缺陷**（这就是"必须真跑一次"的价值）：
   - `fetch` 的网络错误（`ECONNABORTED`）无人接管 → 整个脚本带栈崩溃，已成功的部分
     （tag 已推 / 远端已更新 / packed-refs 已修）与崩溃混在一起，看不出哪些成了；
   - 更麻烦的是 **tag 已推而 Release 未建成会永久漂移**：重跑脚本的入口条件是"有无新提交"，
     而 tag 已推时必然无新提交 → 直接返回，缺失的 Release 再也补不上。补了
     `syncReleaseIfMissing()`：无新提交时顺带检查最新 tag 的 Release 并补建。

### 端到端实测结果

- **v2.7.0**：`--apply` 首次跑 → tag 推送成功（`8d29f59..7428cde`，push 耗时 3m07s）、
  packed-refs 自动同步成功、**Release 创建时网络失败崩溃** → 修复后补建成功。
- **v2.7.1**：修复后完整跑通 **31s** —— tag + push + packed-refs + Release 一次全部成功。

  Releases `v2.7.0/v2.7.1`（v2.5.0/v2.6.0 是规则落地前的历史 tag，无 Release）。
