## 二、必须先读懂的业务背景（禁止误报为 bug）

审查前先确认以下设计意图，凡属有意设计的不作为缺陷上报：

1. **`framework/log` 不反向依赖 `auth`**：`auth` 通过 `setLogContextProvider` 把
   `requestId`/`userId` 注入日志。这是为了避免循环依赖，属有意设计。
2. **`AsyncLocalStorage` 上下文穿透**：`requestContext.getStore()` 在非请求场景
   （启动、定时任务）返回 `undefined`，此时不打 `requestId` 属正常。
3. **认证开关由环境变量控制**：如 `JWT_ENABLED`，关掉时相关分支不执行属正常。
4. **多令牌/多端并存**：同一用户可能在 web/app 多端登录，会话不互踢可能是有意设计
   （需在报告中确认而非直接判错）。
5. **`StpUtil` 命名**：沿用 sa-token 的术语体系，非拼写错误。

## 三、审查维度

### A. 文件组织合理性（本次重点）

| 检查点 | 判定标准 |
| ------ | -------- |
| 单文件行数 | ≤1000 硬限（超限必须拆分）；接近 400 应主动规划拆分 |
| 一文件一模块 | 文件内不应内嵌另一独立模块的完整逻辑 |
| 命名一致性 | 全目录统一风格（当前 `StpUtil.js` 是 PascalCase、其余 kebab-case，需确认是否有意） |
| 职责边界 | 文件名是否准确反映内容；是否存在"万能文件"（如 `session.js` 1393 行需核实） |
| 分层清晰度 | 工具类（`totp`/`signature`/`password-policy`）/ 服务类（`*-service`）/ 聚合出口（`index`）是否各归其位 |
| 循环依赖 | 用依赖图检查 `auth` 内部是否有环 |

### B. 控制流安全

- 禁止用 `err.message.includes()` 做控制流判断（须用 `err.code`）
- 所有异步操作是否有超时保护
- 是否存在"先判断后使用"的竞态（TOCTOU），尤其**令牌校验**与**会话状态读取**

### C. 空值安全

- 所有嵌套访问是否用可选链（`req.state?.user?.userId`）
- `??` 与 `||` 使用是否正确（`0`/`''`/`false` 场景）
- 函数参数是否有默认值

### D. 认证安全（auth 模块的核心风险面）

- **令牌校验**：签名算法是否可被降级（如 `alg: none`）、过期时间是否校验、是否防重放
- **时序攻击**：密码/令牌比较是否使用恒定时间比较
- **Cookie 属性**：`httpOnly` / `secure` / `sameSite` 是否齐全
- **会话固定攻击**：登录后是否重新生成会话 ID
- **权限提升**：`requireRoles`/`requirePermission` 是否在所有入口路径一致生效
- **敏感信息**：密钥/令牌是否可能进入日志（结合 `wb-logkit` 脱敏规则核对）
- **TOTP**：时间窗口是否合理、密钥是否安全存储
- **签名**：是否包含时间戳与随机数

### E. 错误处理

- 所有 `continue`/`return` 跳过路径是否记日志（静默失败检测）
- 异常输入是否有告警
- 错误码是否用 `DOMAIN_ERROR_TYPE` 格式，而非消息文本
- 公共 API 是否做参数校验
- `catch {}` 是否吞掉了关键异常

### F. 并发安全

- 模块级可变状态是否有并发写入风险
- 会话失效/踢人是否有竞态
- 是否有防暴力破解的计数（内存计数在多进程下是否失效）

### G. 注释与文档

- 文件头注释是否有 JSDoc + `@author`/`@since`
- 函数注释是否含参数与返回值说明
- 注释是否与实现一致（**上一轮 log 审查的最大问题类型**）

## 四、工作方式（硬性规则）

1. **先读后判**：完整读取文件内容，不凭文件名或片段下结论。
2. **追踪调用链**：检查 `auth` 的 import 依赖与调用方（至少 2 层），
   确认 `index.js` 对外暴露的接口是否与内部实现一致。
3. **实测优先**：能用脚本验证的（如签名可降级、时序比较、目录依赖环）必须实测，
   不靠"看起来像"。临时脚本放系统临时目录，用完清理。
4. **区分有意设计与缺陷**：属第二节列出的设计意图，不作为缺陷上报。
5. **不修改代码**：本指令只做审查并产出报告；修复是后续独立任务。
6. **修复后验证**：若后续执行修复，必须 `npx eslint`（0 警告）+ 全量测试通过。

### 5.2 文件组织专项结论

```
## 文件组织审查

| 文件 | 行数 | 职责是否单一 | 建议 | 优先级 |
| ---- | ---- | ------------ | ---- | ------ |
```

必须给出**可执行的拆分方案**：拆成哪几个文件、每个文件装什么、新文件名是什么。

### 5.3 每个问题必须包含

- **位置**：`文件:行号`
- **问题**：一句话说明
- **证据**：代码片段或实测输出（不接受"我觉得"）
- **影响**：会导致什么后果
- **建议**：具体怎么改

### 5.4 必须包含「已确认无问题清单」

列出检查过但确认正常的项，防止后续重复排查。

### 5.5 优先级排序

按「危害 / 修复成本」排序给出修复顺序表。
