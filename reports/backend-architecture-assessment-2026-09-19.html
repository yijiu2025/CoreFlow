01总体判断

核心结论

这套架构不需要重构，需要的是补齐三件具体的、可验证的事。 选型上它是「模块化单体 + 严格分层 + 单向依赖守卫」，对当前的业务形态（后台管理 + 风控/防火墙） 是合适且克制的选择 —— 换成微服务只会把现在的确定性问题换成一堆分布式不确定性问题。

真正拖住扩展性与稳定性的，从来不是分层方式，而是三类不体现在任何架构图里的缺陷： ① 单线程事件循环上的同步调用；② 把「进程内状态」当成「全局状态」；③ 关键路径不可观测。

其中 ② 是最危险的一类 —— 它在单实例下完全正确，代码审查看不出来，测试也全绿， 只有当副本数从 1 变成 2 的瞬间才以「重复执行 / 策略不一致 / 通知丢失」的形式暴露。 原有 4 处此类假定，现已消除 3 处，剩 1 处（详见 §04）。

但此刻最该做的不是继续修，而是建立压测基线：没有 P95 / 吞吐 / 池等待 / 事件循环延迟的对照数据， 「已经修好了」只是局部证据，「可以扩容了」只是推断。这是本报告排序第一的建议（§05 P0）。

02架构现状（实测）

形态：单体单进程、Fastify v5 + Sequelize v6 + MySQL + Redis v5，Node ESM。 依赖的外部状态只有两个 —— MySQL 与 Redis；Redis 不可用时降级为进程内实现（这正是 ② 类问题的温床）。

请求处理链路

cookie→ auth Session→ rateLimit→ firewall 五层管道→ guard 三级守卫→ handler→ onSend 日志/连接释放

关键结构事实：防火墙五层拦截（限频 / 封禁 / 挑战 / Bot / 地理围栏）作用在全部请求上， 每层都在同一个单线程事件循环里。这决定了本系统的稳定性特征是 「一个慢调用会拖慢所有请求」——包括健康探针，而探针被拖慢会进一步触发编排层摘流， 放大成整体不可用。§03 的 S1 就是这个机理的实例。

分层约束已有守卫（firewall 层间单向无环、src 不得反向依赖 scripts、 导出位置、测试有效性），且守卫自带反例——「无违规」的结论不是来自一个可能写坏的检测器。 这在本仓是少见的成熟度，它让后续改造不必担心悄悄破坏依赖方向。

一处结构性欠账

框架层已有守卫，但应用层之间仍存在双向依赖（oauth21 ⇄ user）。 它不构成当前故障，但会让「把某个应用域拆出去」这件事在未来变得昂贵。属 §05 P2 的持续项。

03稳定性：三类已被实测揭穿的缺陷

这三类都不在架构图上，共同特征是「读代码看不出来、测试全绿、但真实流量下会出事」。 下表每一项都给出机理与实测数据；数字是修前对修后的对照，不是单侧结论。

编号缺陷与机理实测状态
S1 密码哈希阻塞事件循环
使用 bcryptjs（纯 JS 实现，无原生绑定）。哈希是 CPU 密集操作， 在单线程上执行会把所有并发请求（含健康探针）排到队尾。		 10 并发冻结 774ms → 22ms（改用 crypto.scrypt，走 libuv 线程池）
⚠️ 反例：bcryptjs 的 async 版同样冻结 649ms —— 「改用异步 API 就不阻塞」是错的，只有移出主线程才有效。		 已修复
K1 RSA 密钥生成占用主线程
generateKeyPairSync('rsa', 2048)，且开销随模数超线性增长。		 冻结 53~62ms。
严重度如实说明：只发生在启动与冷路径，无任何路由/脚本调用密钥轮转， 属 hardening 而非紧急缺陷。修它的价值是让「请求路径不留同步 CPU 调用」可被整体 grep 验证。		 已修复
K2 请求路径上的同步磁盘 IO
设备授权页每次请求都 readFileSync 读模板，并在函数体内做三次动态 import。		 同步 IO + 模块解析都在请求路径上 → 改为模块级路径解析 + 异步读 + 生产缓存（非生产每次重读，模板改动即时可见）。 已修复
这一节最值得记住的教训 — 测量方法本身会骗人

monitorEventLoopDelay 按固定分辨率采样，实测把 774ms 的冻结报成 17ms。 据此会得出「bcrypt 没有问题」的相反结论。正确测法是跑一个 10ms 心跳、 取相邻 tick 的最大间隔——阻塞多久，空隙就是多久，无法取巧。 另外该方法的噪声下限约 20ms：无阻塞的异步实现也测到 19~25ms， 所以低于该量级的「差异」不能当结论用。

这条之所以单列，是因为它决定了整份评估的可信度： 用错误的仪器，会把最严重的缺陷判为无问题。

补齐的可观测性

与 S1 同源的问题是「看不到」：Sequelize 连接池状态原本无处可查，配置校验散落在各处。 现在 /v1/health/ready 会带上池快照（maxSize / size / available / using / waiting）， 配置校验收敛为单一真相源（22 个关键环境变量 + 弱密钥黑名单 + 跨字段校验）。 两者都刻意不参与就绪判定——池饱和不该成为摘掉一个正在扛量的实例的理由。 探针是公开端点，因此只放诊断字段，不放任何内部细节。

04扩展性：剩余的一处单实例假定

横向扩展的判定标准很直接：把副本数从 1 改成 2，行为是否仍然正确。 原有 4 处不满足，现在 3 处已修并有可复跑关卡，剩 1 处。

E1 调度器没有分布式锁 —— 每个进程各自按周期跑任务 所有定时任务被重复执行 N 次（对账、清理、种子类任务会互相打架） 已修复
E2 守卫配置是模块级单例，改一次只改本进程 各实例鉴权策略不一致 → 同一个用户在不同副本上权限不同 已修复
E4 连接计数的回收依赖进程内状态，僵尸记录永不释放 计数虚高 → 正常的客户端被误判为超限（改按「最后活跃时间」回收，阈值刻意大于请求超时，避免误删长请求） 已修复
E3 遥测统计与 WebSocket 广播在进程内
monitor.service.js 里 const clients = new Set() 是模块级变量； 统计值在进程内累加。		 ① 监控面板看到的统计偏小（每个实例只报自己那一份切片）；
② 封禁/告警通知送不到其他实例上的浏览器——运维在 A 副本上看到拦截日志，B 副本上的告警静默丢失。		 未做

为什么 E3 与前三处不同

E1/E2/E4 修的是「加实例前的正确性前提」，改法清晰、代价低。 E3 的难点不在技术，而在它是实时的、高频的：

  • 统计外置需要为每个计数点引入一次 Redis 往返，而防火墙的计数在每请求路径上—— 直接照搬会把一个纯内存操作变成网络调用，用吞吐换准确性，得不偿失。需要先做本地聚合 + 周期刷写， 而不是逐请求写。
  • 广播外置要引入 Redis pub/sub：每个实例订阅同一频道、收到后仅投递给本机客户端。 这部分设计是直接的，但要注意「实例既发又收」的重复投递，必须带来源标识去重。
  • 可观测性会变：外置后统计的时效性从「即时」变成「一个刷写周期」， 面板的语义随之改变，需要同步告知使用方——否则会被当成 bug。
关于 E3 的建议

优先级高，但不建议在建立压测基线之前动手（§05：P0 优先）。 理由：E3 的改法涉及热路径，它的收益需要用容器化 + 双实例环境来验证， 而当前压测与容器化载体都还不存在。先有尺子，再改热路径。

一个刻意不做的决定

「把每 IP 连接计数也外置到 Redis」曾被列为候选（E4′），本轮评估结论是建议不做， 这是判断而非遗漏：该计数位于每请求路径，而它是安全控制—— Redis 抖动时要么 fail-open（限流静默失效，安全洞），要么 fail-closed（正常流量被拒，可用性事故）； 进程崩溃还会残留膨胀计数，得再引入 TTL 与漂移修正——那是用新 bug 换旧 bug。 代码里已写明正确缓解方式：按 maxConn ÷ 实例数 配值，或把连接限制前移到边缘（Nginx / ALB）。 后者是标准答案，且不把安全控制绑在 Redis 可用性上。

05提升路线

按「不做会卡住后面一切」的顺序排列，不按工作量排列。

P0建立压测基线 —— 没有它，后面每一步都无法判断得失

目前所有性能结论都是单机微基准（哈希冻结多少毫秒）。它能证明「某处阻塞被消除」， 但回答不了「现在能扛多少 QPS」「扩容一倍收益是多少」「数据库先耗尽还是应用先耗尽」。

要采集的最小集合：P50/P95/P99 延迟、吞吐、连接池 waiting 峰值、 事件循环最大延迟、Redis 往返数、以及错误率随并发上升的拐点。 探针已就绪（池快照在 /ready），缺的是一套可重复的压测脚本与一份留档结果。

为什么排第一：E3 属于热路径改造，没有基线就无法证明它是收益还是回退； 容器化载体也需要基线来定资源规格。

P1消除最后一处单实例假定（E3）

做法见 §04：统计走「本地聚合 + 周期刷写」，广播走 pub/sub 并按来源去重， 同时在文档里同步统计时效性的变化。

验收方式要说清：必须两个真实进程观测—— 一个实例封禁 → 另一个实例上的客户端收到通知；两个实例的统计汇总后与总量一致。 单进程模拟不算数（这类缺陷恰恰只在多进程下暴露，这正是它此前一直没被发现的原因）。

替代方案：如果短期内不打算扩容，可只用边缘限流 + 明确记录该假定， 把 E3 降级为「扩容前置项」。可以接受，但必须在文档里写成「已知限制」而不是「已支持多实例」。

P2数据层与耦合度（持续项，随迭代做）

这三项都不会立刻出事，但都会随时间变贵：

  • 索引与查询计划取证：为高频查询补索引前，先用 EXPLAIN 确认真实执行计划—— 「按直觉加索引」在本仓的高频陷阱里已记为一类错误。
  • 拆分 session.js（994 行）：它同时承担创建/验证/销毁/续期/刷新/踢下线， 是安全敏感路径上最容易改出问题的文件。拆的时候用按行号切片的脚本 + 四条断言，不要手工复制。
  • 收敛应用层双向依赖（oauth21 ⇄ user）：当前不痛， 但它是「未来想把某个域拆出去」的主要成本来源。
P3容器化与 CI 载体 —— 先有能验证的环境，再产出制品

部署文档里描述的 Docker 与多服务器方案，代码里并不存在。 本仓刻意没有提交未经验证的 Dockerfile / CI 配置—— 未经验证的制品比没有制品更危险，因为它会让「能扩容」变成一个看起来成立的假设。

正确顺序：先有可用的验证环境（能起双实例、能跑压测），再产出容器化与 CI。 这也是 P0 排在最前的原因之一。

不建议做的

不要微服务化。当前瓶颈是单进程内的同步调用与进程内状态，不是「服务边界不清」。 在这个阶段拆服务，只会把确定的局部问题换成一堆分布式问题（网络不确定性、分布式事务、跨服务追踪）， 而当前团队尚无压测基线与容器化载体——那会是一次净损失。

06本报告的结论是怎么来的

对一份评估报告来说，「怎么得到结论」比结论本身更值得审查—— §03 那条测量陷阱已经说明，用错仪器会把最严重的问题判为无问题。

手法解决的信任问题
毒丸实验 把被测文件换成 throw 再跑测试：变红 = 测试真的加载了被测代码； 照绿 = 测试完全失效。用于排除「测试全绿但其实什么都没测」。
反例对照 证明「现在能过」不等于证明是对该修复起效。每条修复都同时跑一条不做修复的同场景用例 （如 S1 里 bcrypt 的 async 版本同样冻结）。
真实多进程 E1 用 5 个真实进程抢同一把锁，验证「恰好 1 个成功 / TTL 内抢不到 / 过期后能抢到」三轮—— 缺任一轮都会漏掉一种失败（如「拿到就不放」与「永远拿不到」在只验第一轮时表现相同）。
可复跑关卡 把一次性验证固定成 npm run verify:all，退出码区分 0 通过 / 1 断言失败 / 2 回滚不完整 / 3 环境不可用。 刻意把「环境不可用」与「回归」分开——环境问题也让检查变红，会让它变成长期红灯的检查， 而长期亮红灯的检查等于没有检查。
危险操作护栏 会写真实库的验收关卡：先取全量快照、空快照时在任何写入之前退出 （回滚实现是清空全表 + 回填，空快照会把配置表清空）、拒绝在生产环境运行、结束无条件回滚并回读核对。

基线：77 个测试套件 / 1020 个用例全部通过；改动文件 lint 0 error 0 warning； 「虚假覆盖测试」的冻结清单只减不增（本轮已减至 14），防止新增虚假覆盖。

07尚未验证的事情

以下都不是「大概没问题」，而是当前没有证据。列出来是为了让它们不被当成已完成。

  • 真实负载下的行为：所有性能数字都是单机微基准，无压测基线。 「修复有效」有证据，「足以支撑扩容」没有。
  • E3 未做：遥测统计与 WS 广播仍在进程内，多实例下统计偏小、跨实例通知丢失。 这是目前唯一剩余的横向扩展阻断。
  • 连接池容量在上限处的表现：max=10/实例，MySQL 默认 max_connections=151， 因此理论上约 15 个副本就会耗尽连接。该约束已写成代码注释，但没有在接近饱和时实测过。
  • connectStandalone() 的重试语义与注释不符：注释写「CLI 场景最多重试 1 次」， 实际由客户端 reconnectStrategy 决定（默认 10 次，Redis 不可达时约 90 秒才返回）。 已在验收关卡里用有界前置检查绕开，源码本身未改——是否修正应由代码所有者决定。
  • 容器化与 CI 载体不存在：未提交任何未经验证的制品。
一句话

前三轮修复清掉的是「会让多实例行为不可预测的代码缺陷」。 「因此现在可以加机器了」这句话，需要一次真实的双实例压测来宣布，而不是由本报告代为宣布。
