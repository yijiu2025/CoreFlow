01结论

三句话：

Verdict

① 机制主体是健康的。「一个主题包 = 一种版式」这条 2026-09-26 的收窄是对的， 它消灭了「换版式要复制整套配色」的漂移源；三级 glob（包定义 / 配色 / 版式）让 加配色、加版式包确实无需改任何源码文件。这一点已经不欠账。

② 但「不需要配置」的瓶颈不在源码，在关卡。 真正拦住 drop-in 的是 .tmp-probe/verify-theme-dirs.mjs 里 PEER_COLORS = ['black','white']（L68）与 if (pkg === 'compact')（L195 / L417-418） 这类写死的包名与颜色名——新增一个只覆盖部分设备/页面、或只带一套自命名配色的主题包， 必须回来改关卡脚本。关卡即配置，这才是要拆掉的那道墙。

③ 有一个 P0 级静默失效已经发生，而且被"失修关卡"掩护了。 theme/views/pages.ts L67 的鸭子类型判据要求 list() 方法， 而该方法已在 8f6b328 随变体机制删除 → 判据恒假 → 调试面板的「版式」区永远不会渲染，且全程零报错。

03缺陷清单

P0-1 鸭子类型判据滞后于接口：调试面板的「版式」区永久失效（静默） oauth21/src/theme/views/pages.ts:61-70（判据）· L67（candidate.list）｜仓库 .tmp-probe/verify-panel-v3.mjs:72,135,160（掩护它的失修关卡）

证据链（三步，全部可复核）：

  1. git log -S "list(" -- oauth21/src/theme/views/registry.ts → 提交 8f6b328 删掉了 list(pkg, device): string[]；
  2. 当前 registry.ts 的返回值只有 { baseId, builtinPackage, packages(), has(), resolve(), load() } —— grep -n "list" src/theme/views/registry.ts 零命中；
  3. 而 pages.ts L67 仍在判 typeof candidate.list === 'function'， 且 git log -S "candidate.list" 显示该方法从未被删过（只有添加它的 4aa5317）。

    → viewsForPage(page) 恒 undefined

      → panel: activeViewId 退化成 themeStore.packageId

为什么长期没被发现：唯一能抓到它的关卡 verify-panel-v3.mjs 自己已经过期 —— L72 断言 B2 含 base、L135 E0 register 列出 base + compact、 L160 E5 切回 base，而 2026-09-26 起 view ≡ pkg，面板列的是 包名（default / compact）。该关卡长期是红的， pages.ts 的红被淹没在里面。这是「关卡自己也在骗人」的第二个实例 （第一个是上一轮 PWA 的流量探针看不见 SW 流量）。

关键设计判断

修法不能只是"把 list 换成 packages"—— 那只是把同一个坑填上， 下次接口一变又会静默落后。正确修法是让判据由接口派生， 使"判据落后于接口"在编译期就不可能发生：

// pages.ts —— 成员清单与 ViewRegistry 同源，缺一项 TS 直接报错
const MEMBER_KINDS: Record<keyof ViewRegistry, 'string' | 'function'> = {
  baseId: 'string', builtinPackage: 'string',
  packages: 'function', has: 'function',
  resolve: 'function', load: 'function'
};
// Record<keyof ViewRegistry, …> 提供穷尽性：接口加成员而不在这里分类 → 编译失败
function isViewRegistry(value: unknown): value is ViewRegistry {
  if (!value || typeof value !== 'object') return false;
  const c = value as Record<string, unknown>;
  return Object.entries(MEMBER_KINDS).every(([k, kind]) => typeof c[k] === kind);
}

验收：新增行为断言（不是静态 grep）—— 在浏览器里 import('/src/theme/views/pages.ts') 后断言 pageFromPath('/login') === 'login'、pageFromPath('/mini-login') === 'login'、 且 /m/register 上面板 [data-view-id] 至少含 default 与 compact。并毒丸验证：把判据里任一成员名改错，关卡必须变红。

P0-2 「关卡即配置」：写死的包名与颜色名，恰好挡住了 drop-in .tmp-probe/verify-theme-dirs.mjs:68 · :195 · :417-418

关卡里有两类硬编码的例外：

  • L68 const PEER_COLORS = ['black','white'] —— 断言 每一个「包 × 设备 × 页面」下都必须同时存在 black 与 white；
  • L195 / L417-418 if (pkg === 'compact' && device !== 'mobile') continue; —— 把「compact 只覆盖 mobile/register」这条数据性事实写成了代码里的 if。

为什么这正是你要拆的那道墙：theme 目录本身已经做到了 drop-in （glob 自动登记），但一个新的、只覆盖部分范围的主题包会因为 PEER_COLORS 而变红，一个只提供一套自命名配色的包同理 —— 于是作者必须回来读并修改一个 1125 行的探针脚本。「放进去就能用」在这一步断掉了。

方向

把「例外」从 if 变成包自己声明的数据（见 §06）。 声明与实现同目录 → 只放那一套文件即可；关卡改为读声明推导期望， 删掉 PEER_COLORS 与全部 pkg === 'compact' 分支。

P1-1 外部输入一致性缺口：applyThemeConfig 的 mode 没过白名单 oauth21/src/stores/theme.ts:839｜对照 oauth21/src/theme/remote.ts（同字段做了 normalizeMode）

证据：后端那条路（remote.ts 的 normalize()） 对同一份 JSON 做了 normalizeMode(raw.mode)；但 store 的 applyThemeConfig() 第 839 行是裸赋值：

if (config.mode && !urlLockedMode) mode.value = config.mode;   // ← 未经 normalizeMode

可达路径：composables/useParentThemeSync.ts:74 （iframe 父应用的 postMessage）进的正是这个方法。父页面虽然受信 （origin 过白名单），但 postMessage 载荷在浏览器里终究是外部输入 —— 这一点项目自己在同一文件的注释里写明过（tokens 就是按这个理由逐条校验的）。 tokens 校验了、mode 没校验，是同一威胁模型下的不一致。

后果：非法 mode 写进 store 后 —— MODE_LABELS[mode] 变 undefined（面板头部显示空白）、 MODE_CYCLE.indexOf(mode) 变 -1（「循环明暗」按钮跳回 'system'， 看着像随机行为）、syncColorToTone 的判定落空。

修法：与 remote.ts 同口径， const m = normalizeMode(config.mode); if (m && !urlLockedMode) mode.value = m; —— 并把 RemoteThemeConfig.mode 的类型收紧为「已归一化」以示区分。

验收：页面内 import() 到 store 后调 applyThemeConfig({ mode: 'DARK' }) 与 { mode: 'zzz' }， 断言 __MAUTH_STORE__.mode 未被写成非法值；现有关卡 verify-theme.mjs G 段（后端下发优先级）可扩一段覆盖它。

P1-2 面板「恢复默认」实际落到 black，与「默认配色 = white」的口径相反 oauth21/src/components/dev/ThemeDebugPanel.vue:357-361 
function resetAll(): void {
  themeStore.setMode('system');          // ① 先写 system
  const first = colors.value[0];       // ② colors 按 id 字母序 → [0] === 'black'
  if (first) themeStore.setTheme(first.id);  // ③ setTheme 又把 mode 改成该色系别 = 'dark'
}

两处问题叠在一起：① setTheme 会把 mode 同步成配色的系别， 所以前面那次 setMode('system') 立刻被覆盖，「恢复默认」并没有回到「跟随系统」； ② colors[0] 是字母序第一 —— black < blue < cyan < rainbow < white → 落到 black。 这恰好是 DEFAULT_THEME_COLOR 当初专门引入要消灭的那个事故 （"字母序第一 → 默认外观落在黑系"），在调试工具里原地复现了。

修法：顺序反过来并走显式常量 —— themeStore.setTheme(DEFAULT_THEME_COLOR) 后再 setMode('system')； 或让 resetAll 只清 localStorage + 重载，不在 UI 层复刻选择逻辑。

P2-1 默认参数自相矛盾：themeRecordFor() 的 pkg 与 view 默认值不同源 oauth21/src/stores/theme.ts:362-370（签名）· :750（packageId）· :287（isDark）· :344（activeTone）

  page   = activePage.value,

当 activeView 是 compact 时，签名自相矛盾 （"包 = default，版式 = compact"），精确键必然 miss， 只能靠 theme/index.ts findRecord() 的 ②兜底全表扫描碰对。而 packageId、isDark、 activeTone 三个 computed 全部建在它上面 —— 正确性靠巧合、性能靠运气。 这不是当前会出错的地方（兜底确实能碰对），但它把所有派生访问器都拴在了兜底分支上， 任何一次"收紧兜底"的优化都会立刻打断它们。§07 的 view 清理会从根上消掉它。

P2-2 注入器的变量名清单可能含重复项 oauth21/src/theme/runtime.ts:81-94

applied 是普通数组：同一个 token 名同时出现在主题层与外部覆写层时会被 push 两次，injectedNames 随之含重复。清理时多调一次 removeProperty 无害，但 getInjectedTokenNames()（验收脚本在读它） 会返回长度虚高的清单 —— 断言"注入了 N 个变量"的关卡可能被这个虚高骗过。 修法：injectedNames = [...nextNames]（复用已有的 Set）。

P2-3 残留物：28 文件的旧主题树备份 + 162 个探针脚本 oauth21/.tmp-probe/_backup-color-headers/src/theme/themes/（28 个 .ts/.scss）｜.tmp-probe/ 135 + oauth21/.tmp-probe/ 27

_backup-color-headers 是 fix-color-headers.mjs 留下的整棵旧主题树副本。它不影响关卡（关卡只扫 join(HERE,'..','oauth21','src')，见 verify-theme-dirs.mjs:54）， 但它是"这份仓库里有两份 themes/ 树"的假象来源，建议清掉。 探针脚本 162 个而 README 只认 8 个是"关卡" —— 其余 154 个是历史一次性探针， 其中已有多个过期（verify-theme.mjs 靠末尾自检 exit 2 兜着，面板三件套则没有这种保护，于是淹没了 P0-1）。

读法

第 2 行是最高性价比的修复对象：源码侧已经做到了 0，唯一的障碍是关卡里的 if。把 P0-2 修掉，"加一个只覆盖部分范围的主题包"就变成真正的 drop-in。

第 3 行（新页面）才是"架构文件放进去就能用"的完整版，它需要一个 页面描述表把三份同形页面文件收口（见 §08 优化项 O4）—— 按你的选择，这一档本轮不做，但方案里给出形态，以便下一轮决定。

06方案 A（P0）：主题包自描述——把「例外」从 if 变成数据

这是拆掉 P0-2 那道墙的落点。核心原则： 声明必须与实现住在同一个目录里，否则"放进去就能用"又会变成"放进去再改别处"。

6.1 形态：themes/<包>/index.ts 增加可选的 coverage

// oauth21/src/theme/themes/compact/index.ts
export default {
  meta: { id: 'compact', name: '紧凑版' },
  views: { register: 'compact' },
  // 🆕 自描述覆盖范围 —— 不写 = 全设备 / 全页面 / 要求 black+white（即现行口径）
  coverage: {
    devices: ['mobile'],           // 只做手机端
    pages:   ['register'],          // 只做注册页
    colors:  { min: 1 }                  // 不强制 black+white，至少 1 套
  }
} satisfies MauthThemePackage;

字段语义（都很小，能被关卡机械推导）：

字段不写时的默认关卡据此断言
coverage.devices全部 THEME_DEVICES该包在每个列出设备的每个列出页面下都必须有 index.vue
coverage.pages全部页面（= views/*.ts 的页面集合）同上；未列出的设备/页面不参与断言（替代 pkg === 'compact'）

  const need    = decl.coverage?.colors?.require ?? ['black', 'white'];
  for (const d of devices) for (const p of pages) {
    if (!hasView(name, d, p)) continue;      // 声明覆盖但没实现 → 由下面单独报
    assertColorsContain(name, d, p, need);      // ← 不再有 PEER_COLORS
  }
}
为什么这是对的形态

① 删掉的是"例外"，不是"检查" —— 默认值仍是现行口径，检查强度不变； 变的只是"例外从哪来"。② 声明与实现同目录， 复制一个主题包时声明跟着走，不会出现"新包忘了在某处登记例外"。 ③ 它同时是最好的文档：打开 themes/compact/index.ts 就知道这个包覆盖什么，不必去读 1125 行的探针。④ 未来若要支持"外置主题包"（选项 C）， 运行时需要知道的正好就是这几项 —— coverage 是那条路的前置条件。

6.3 兼容与风险

  • 完全向后兼容：coverage 可选，两个现有包不加也能跑（等价于现行口径）。
  • 类型面：MauthThemePackage 加一个可选字段，属加面不是改面， 不影响 import type 的调用点；内核包只加类型不加逻辑（零运行时依赖不变）。
  • 风险：声明与实现不一致时（声明覆盖但没实现）必须明确报错而不是静默 —— 这是这套方案唯一的新失败模式，关卡要有一条专门的断言。
