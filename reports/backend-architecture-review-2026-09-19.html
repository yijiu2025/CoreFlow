01总体结论

核心判断

分层设计是健康的，不需要推倒重来。系统层 / 应用层 / 路由层边界清晰，依赖方向有测试守卫， 会话层已经完全 Redis 化 —— 这是最关键的资产，意味着认证层本身已具备横向扩展能力。

真正阻碍扩容的不是"架构选型错"，而是 4 个进程内状态散落在子系统里， 外加 1 个此前未被发现的事件循环阻塞点。这些都是定点可修的，不需要架构手术。

最关键的一条决策建议：在上述阻断项修完之前，增加机器不会提升容量 —— 反而会让定时任务重复执行、守卫配置实例间不一致、遥测统计互相覆写， 使系统从"慢"变成"行为不可预测"。

03扩展性阻断项

这 4 项的共同特征是：状态存在单个进程的内存里。多跑一个实例，状态就分裂成两份， 而且不会有任何报错 —— 只会表现为行为怪异。我把每一项都回到代码里确认过当前状态。

E1 定时任务无分布式锁：每个实例都会重复执行 未修

调度器用 setInterval 本地计时，且启动时立即执行一次：

src/framework/scheduler/index.js:93-101

const run = () => { taskFactory.run(app, taskConfig).catch(...) };
run();                                    // ← 启动即跑
const timer = setInterval(run, intervalMs);

多实例后果：N 个实例 = 每个周期执行 N 次清理。当前任务量小，问题被掩盖； 一旦加入"发通知""对账"这类有副作用的任务，就会出现 N 份重复。这类故障不报错， 只表现为"数据库负载莫名变高"。

关键发现

修复成本几乎为零：src/framework/redis/lock-store.js 已经存在（4.7 KB，含 SET NX PX 语义）， 但全仓零引用 —— 调度器、业务代码都没有用过它。这是一个"能力已备好、只差接线"的状态， 属于典型的低垂果实。

E2 守卫配置是模块级单例，多实例下会造成鉴权结果不一致 未修

src/api/guard-config.js:22 持有 let configs = {}， 而 loadGuardConfig() 只在启动时被调用一次（全仓仅 :37 一处 GuardConfigDao.loadFromDB()）。运行期修改走"防抖 + 异步写 DB"， 只更新写操作所在实例自己的内存。

这是安全语义问题，不只是可用性问题

运维在管理面板上"关闭某个路由的鉴权"或"收紧 IP 白名单"，只有部分实例生效。 同一个请求打到 A 实例和 B 实例，会得到不同的鉴权结果 —— 这在安全审计里是无法解释的。而且没有版本号轮询，B 实例直到重启前都不会自愈。

修法：DB 里已有 version 字段与乐观锁实现，直接复用即可 —— (1) 短期：每实例定期比对 version，变化即重载； (2) 中期：运行时读取改走 getStore('guard')，DB 只负责持久化，天然一致。

落盘写入的原子性已解决（tmp + rename，临时文件名带 pid），且补了优雅关闭落盘。 所以在单实例下这条不再是数据丢失风险。剩下的纯粹是"多实例视图分裂"问题。

修法：统计改 Redis Hash + HINCRBY；WS 广播改 Redis Pub/Sub。 若判断成本过高，退而求其次的诚实做法是：在管理面板明确标注"统计为单实例视角"， 而不是让运维误以为那是全局数字。

E4 每 IP 并发连接计数在进程内，限流语义被实例数放大 未修

activeConnections 是模块级 Map（app/firewall/util/shared.js:28）。 多实例下每个 IP 的实际可用连接数变成 maxConn × N —— 配置写的是 10，实际放行了 N×10。这是一个安全配置被静默放大的问题。

另有清理逻辑缺陷：cleanupStaleConnections() 只删除计数超过阈值 2 倍的记录， 且每 5 分钟才跑一次。若某 IP 因异常路径（未走到 onSend）泄漏了 1~2 个计数， 永远不会被回收，该 IP 会被持续额外扣减配额。

修法：计数改 Redis INCR/DECR + TTL；清理判据从"计数阈值" 改为"最后活跃时间"，这才是与泄漏正交的判据。

04稳定性风险

这一组问题在单实例下也会发生，因此优先级不低于上面的扩容阻断项。 其中 S1 是本轮新发现，也是本次评估里性价比最高的一个修复点。

S1 同步密码哈希阻塞事件循环 60ms —— 并发登录会拖垮整个进程 本轮新发现

项目用的是 bcryptjs（纯 JavaScript 实现，无原生绑定）。 它的 hashSync / compareSync 会完全占住主线程 —— Node 单线程模型下，这 60ms 内所有其他请求（含健康探针）全部排队。

本机实测（cost=10）：

单核理论上限

生产代码中的 4 个同步调用点：

位置场景触发频率
app/user/dao/user.js:100compareSync 登录校验高 · 公网可触发
app/user/dao/user.js:179hashSync 注册高 · 公网可触发
app/user/dao/user.js:280hashSync 重置密码中
app/oauth21/dao/client.dao.js:57hashSync 客户端密钥低（管理操作）
为什么这是 DoS 放大面而非单纯性能问题

登录接口公开且无需认证。约 50 个并发登录请求即可造成约 3 秒的完全停顿 —— 而 /v1/health/ready 的探测超时恰好是 3 秒。 于是：一次登录流量突发 → 探针超时 → 编排系统判定实例不健康并摘流 → 流量涌向剩余实例 → 雪崩。防火墙的每 IP 限流对此无效，因为攻击可以分布式发起。

作者做对的一点（应予肯定）

hashSync 在 user.js:179 被放在事务之前（事务从 :182 开始）。 这避免了"数据库连接被 CPU 密集操作占用 60ms"的复合反模式 —— 顺序是对的，不要改动这个结构。

修法（按推荐度）：

  • 换原生 bcrypt（N-API）：异步版本跑在 libuv 线程池，完全不阻塞事件循环， 哈希格式兼容、可直接复用现有数据。代价：需要编译工具链或预编译二进制。
  • 改用 Node 内置 crypto.scrypt：异步、在线程池执行、零第三方原生依赖，是 Node 官方推荐方案。 代价：格式不同，需要"下次登录成功时透明重哈希"的迁移策略。
  • 最低成本兜底：保留 bcryptjs 但改用 bcrypt.hash / bcrypt.compare（异步版）， 配合并发信号量限制同时在算的哈希数。比 sync 好，但仍是主线程 CPU 消耗， 只是把长阻塞切成短让步。
  • 另建议把 cost 因子做成环境变量 —— 现在硬编码 10，无法在压测时调优。
S2 没有任何部署制品与 CI —— 扩容缺少可复现载体 未修

实测 Dockerfile、docker-compose.yml、.github/ 三者均不存在 （今日已把文档里的"已完成"标记改正为"设计稿 · 未实现"，这一点值得肯定）。

为什么这是扩容的前置条件：没有可复现的构建产物，"加实例"就只能靠手工在机器上 git pull && npm install —— 这会导致实例间依赖版本漂移、环境变量不一致， 而多实例架构恰恰最怕"实例之间不一样"。先把构建固化成镜像，扩容才有讨论基础。

S3 每实例额外 105MB 常驻内存（geoip-lite 全量加载） 本轮新发现

geoip-lite 在 require 时把整个 IP 库全部加载进内存， 且数据存在 JS 堆之外（heapUsed 只涨 0.4MB，全在 RSS 里）。实测：

场景RSS增量
裸 Node 进程42.7 MB—
加载 geoip-lite 后148.0 MB+105.3 MB

影响：扩容时每实例内存基线是 ~150MB 起步（还没算连接池与请求负载）。 若容器内存上限设成 256MB，会在压测中 OOM，且 OOM 现场看不出与 IP 库有关。 使用点：app/firewall/engine/detectors/geo-filter.js:8,29,85。

处置：容器内存下限按 512MB 规划并写入部署文档； 若要压缩，可改用 MaxMind mmdb + LRU 缓存的按需查询，或把地理判定拆成独立小服务 （但这会引入网络跳转，需权衡）。本项不紧急，但必须在定容量规格之前知道这个数字。

S4 连接池默认 10，与实例数无协调；池状态无法观测 本轮新发现

src/framework/db/index.js:50-55：

pool: {
  max:     parseInt(process.env.DB_POOL_MAX     || '10'),   // 每实例 10
  min:     parseInt(process.env.DB_POOL_MIN     || '2'),
  acquire: parseInt(process.env.DB_POOL_ACQUIRE || '30000'), // 等 30s
  idle:    parseInt(process.env.DB_POOL_IDLE    || '10000')
}

两个具体风险：

  • 容量天花板被写死：MySQL 默认 max_connections = 151。 按每实例 max=10 计算，约 15 个实例就会耗尽数据库连接。 正确做法是让池大小成为实例数的函数：max ≈ (DB_max_connections − 保留) ÷ 预期实例数， 并把该算式写进部署清单。
  • 故障根因被掩盖：acquire 是 30 秒，而探针超时是 3 秒。 池枯竭时，探针会在自己的 3 秒超时里被掐断，对外表现为"探针不稳定"， 而真实原因（连接池耗尽）根本不会出现在任何日志或指标里。这正是最难排查的一类故障。

修法：把 sequelize.connectionManager.pool 的 size / available / pending / using 暴露到 /v1/health/ready 的响应体（注意脱敏，该端点是公开的） 或独立的内部指标端点。有了这个数，"变慢"才能被归因。

S5 15 个"虚假覆盖"测试仍在冻结清单中 存量

src/__tests__/conventions/test-effectiveness.test.js:49-65 的 KNOWN_INEFFECTIVE_TESTS 当前冻结了 15 个测试文件。这些文件的特征是 不加载被测代码 —— 把被测模块整个删掉，它们依然全绿。

其中包括 config-validation.test.js、permission-loader.test.js、 rate-limiter.test.js、security.test.js —— 覆盖的恰好都是 配置校验、权限加载、限流这些与本报告主题直接相关的领域。

必须说清的一点

有守卫测试把清单冻结为"只减不增"，这本身是成熟做法（说明团队知道问题存在，且防止恶化）。 但要注意：这些领域的"绿灯"目前不能作为稳定性证据。 在评估扩容风险时，不能把它们的通过计入安全边际。

05明确不建议做的事

架构评审的一半价值在于说清"不该做什么"。以下动作在现阶段属于过度设计，会消耗资源且掩盖真问题。

  • 现在就拆微服务。四个阻断项全是"进程内状态"问题 —— 拆成服务只会让它们更难定位， 而且当前没有镜像、没有 CI、没有就绪探针，拆完根本无法运维。
  • 引入 Kubernetes。K8s 的收益（滚动发布、自愈）完全建立在就绪探针之上。 探针已就位，但调度器锁与配置同步没做之前上 K8s，只会让实例间的行为差异被自动放大。
  • 引入消息队列（Kafka / RabbitMQ）。全仓只有 1 个定时任务，没有异步任务队列需求。 现有 framework/redis/queue-store.js 已覆盖轻量场景。
  • 把 Session 改成无状态 JWT。当前"Redis 会话 + JWT 对外 API"是正确混合。 改成纯 JWT 会丧失主动踢下线能力，是明确的能力倒退。
  • 全面迁移 TypeScript。与扩展性、稳定性无关。41K 行无构建步骤的代码库迁移本身 会引入大量风险，收益却滞后。
  • 在阻断项修完之前加机器。这是本报告最重要的一条。 加实例得到的不是容量，而是行为不可预测 —— 统计错乱、任务重复、鉴权不一致。

08证据复核方法与报告边界
