Frontend Architecture Review

前端架构评审：可维护性、可读性与安全

评估对象 oauth21 及其所在的 nodeServers mono-repo 前端面 （oauth21 · posecraft · firewall · packages/*）。技术栈 Vue 3.5 + Vite 8 + Pinia 3 + TypeScript strict。 本报告基于代码级独立取证：依赖审计、配置与源码静态统计、既有验收关卡实测。 每条结论都附可复核的命令或数字，不做印象式评价。

评估日期 2026-09-27 方法：npm audit + 静态统计 + 关卡实测 oauth21 129 源文件 3 前端工程 / 3 工作区包 审计 34 项（1 严重 · 15 高危）

01总体结论

核心判断

设计是健康的，问题几乎全在工程化。这套前端的架构意识明显高于平均水平： 主题 / 设备 / 版式三个正交维度拆得干净，"一个主题包 = 一种版式"这条约束被落成了可执行断言； 依赖方向（themes → 容器 → theme-vue → theme-core）有静态守卫； 验收关卡能自己变红（毒丸验证 8/8 命中）。这些都是"设计对了"的证据， 不需要推倒重来。

真正拖后腿的是三条工程化缺口，且互为因果：

① 生产依赖带 1 严重 + 15 高危漏洞，且没有任何机制会提醒你 —— @fastify/static 的路径穿越可绕过路由守卫、nodemailer 可被注入邮件头， 两者都在生产请求路径上。

② 三个前端工程完全不在 CI 里 —— 类型闸门、ESLint、主题关卡全部只在本地跑。 后端有 3 条 CI 作业 + 82 个测试文件，前端是 0 条作业 + 4 个测试文件。这个落差是整份报告里最大的一处。

③ 依赖不可复现 —— package-lock.json（847 KB）被 .gitignore 排除， CI 只能靠 --legacy-peer-deps 现算整棵依赖树。根因是 packages/log 是个不在 .gitmodules 里的嵌套 git 仓，lockfile 无法整体入库。

一句话结论：这是一套"设计 4 星、工程化 2 星"的前端。 把 CI 补上、把漏洞修掉，综合分能从 72 走到 85 以上，而不需要动一行架构。

03架构分析：哪里是对的

先把"不需要动"的部分说清楚 —— 否则后面的整改建议容易被误读成"架构要换"。

图 1 · 分层与依赖方向、三个正交维度、版式取值链。虚线框内是本轮刚抽出的内核包。

做对了的三件事（建议保留，别在重构里丢掉）

  • 约束被写成了可执行断言，而不是文档里的君子协定。 "页面下不允许有版式层目录""每份版式都要带 data-mauth-view 且值等于包名" —— 这些都以静态断言形式存在（verify-theme-dirs，552 项）， 并且配了毒丸脚本反过来证明"断言真的会红"（8/8 命中）。 大多数团队的 lint 规则是恒绿的摆设，这里不是。
  • 内核与宿主分离的边界画对了。 packages/theme-core 只放纯叶子层 （常量 / token 校验 / 色调 / 模式 / 类型 / 设备参数），并明确禁止出现 import.meta / window / document / localStorage。 这让"内核知不知道宿主"变成一条可 grep 的规则，而不是靠人自觉。
  • 性能不靠感觉，靠关卡 —— 但这次评审也证明"关卡本身会骗人"。 首屏请求清单（dev 口径）确实守住了"页面自己按需加载"这一层，且它会真红。 可"再加一条 PWA 预缓存 KB 关卡"这个组合没能救场：它读的是 sw.js 清单的 体积，而真正量流量的 measure-load-budget.mjs 把 CDP Network.enable 挂在 page target 上 —— SW 发出的请求它一个都看不见 （SW 的 install 跑在独立 target）。于是"屏蔽 SW"与"不屏蔽"两轮数字一字不差， 还报出"清单里首访不会请求的有 0 项"这种自我安慰的结论。 教训：关卡要能证明自己量得到东西，毒丸思维对新关卡同样适用。
顺带纠正一个常见误读

theme/views/*.ts 那几个文件看着"很大"（login.ts 15.6 KB）， 但实测代码只有 98 行（236 行里 178 行是注释/空行）。它们并不臃肿， 臃肿的是注释。见第 07 节。

结论

改样式、换配色、换版式都很轻（1–4 个文件，且不动代码）；重的是"新增一个业务页"（14–18 个文件）。 这个分布其实是合理的 —— 它把复杂度压在了"新增功能"这种低频操作上，而不是"调外观"这种高频操作上。

真正让使用变繁琐的是两处隐性知识：① 多 Vite 实例必须串行启动（否则 504 白屏）； ② 沙箱/本机环境下构建必须用全新 outDir。这两条都只存在于项目内部记忆里， 应该搬进 README 或 docs/，否则每个新人都会各自踩一遍。

为什么"34 项漏洞"这件事本身比漏洞更值得注意

这个项目在代码层做了大量安全防护（禁 v-html/eval、 白名单化 iframe 父 origin、用类型谓词收窄、密码用 crypto.scrypt 替掉 bcryptjs 的阻塞实现）， 但在依赖层连"有漏洞"这个事实都没有人被告知 —— 根 package.json 里 有 audit 脚本，却没有 CI 作业或定时任务去跑它。 建议：在 CI 加一条 npm audit --omit=dev --audit-level=high， 或接一个 Dependabot 配置。否则这类问题永远靠事后发现。

注释里记的是成因与实测数据，不是"这是一个 ref"这种废话。典型例子： 为什么必须换掉 bcryptjs（附 774ms / 649ms / 164ms 三组实测与"不要用 monitorEventLoopDelay 量"的警告）、为什么 CI 不能用 npm ci、 为什么不能用 monitorEventLoopDelay。 这类注释的边际价值极高 —— 它把"为什么这么写"从口头传承变成了仓库资产。

但代价也是真实的（三条）

  • 注释与实现会漂移，而且已经漂了。 本次评审就抓到一处：verify-theme.mjs 的期望值仍按 ocean/graphite 两套早已改名的配色写（38 项失败）。同一份仓库里，"文档承诺的环境变量名"也曾与实现不符。 建议：长注释里凡是"数值/名字/路径"这类会过期的事实，要么写进可执行断言，要么只留规则 + 指向 docs/，别把实测数据抄进源码。
  • 浏览成本高，改代码时要在注释里"捞"代码。 75% 注释占比意味着打开文件先看到三屏解释。register.ts 里有效代码只有 58 行， 但文件有 236 行 —— 改一行要滚动很久。
  • 文件体积被注释推大，掩盖了真实结构。 login.ts 显示 15.6 KB 时难以判断它是不是上帝文件；实测代码只有 98 行才松一口气。 这种"看起来很大其实不大"会让评审者错判。
